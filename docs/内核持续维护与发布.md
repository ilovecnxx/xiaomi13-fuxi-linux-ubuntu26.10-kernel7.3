# 内核持续维护与发布

## 基线与更新规则

标准源码配方基线为 `7.4.0-rc1-fuxi-std2`。最近实机记录（2026-11-14）为运行/默认 deb9、回退 deb8；
设备包 `0.20261114.1701` 已通过迁移和重启验收，内核未更换。std2/chg3 是历史部署组合，
不应当作当前设备配置。状态入口见 [TASKS.md](../TASKS.md)。
RC 内核归入实验通道，不称为长期支持版本。每周检查 kernel.org 对应分支更新和安全公告；
已确认影响本机的高危问题在 24 小时内评估，目标 72 小时内完成候选构建，不能满足时记录原因。
每次修改 `kernel/manifest.json` 必须同时更新上游压缩包哈希、补丁、完整树哈希和验收记录。

升级下一 RC、正式版或 stable 补丁版时先在独立目录重建并重放补丁，移除已上游合入的改动。
优先采用能保留已验证硬件支持的正式 stable 分支；LTS 只在驱动覆盖和移植成本经过验证后选用，
不为追逐版本号自动替换默认内核。实验构建始终使用唯一名称，禁止复用已发布的包版本或启动条目。

## 晋级检查

1. 固定构建环境中源码校验、主机回归、定向 W=1 与 DT 检查通过；保留完整警告结果。
2. 独立内核 deb 安装、initrd、DTB、条目校验和及自动回退通过；至少保留一个已确认旧内核。
3. 冷启动、重启、显示/触摸、桌面输入、WiFi/传感器、双卡注册、基础音频和实际充电复验。
4. 挂起策略有改动时加测恢复、网络重连和来电唤醒；充电改动增加低电量持续充电与温度记录。
5. 连续运行至少 24 小时及 10 次正常重启，无新增崩溃、存储错误和服务失败。
6. 记录源码树、包哈希、配置、构建环境、已知功能缺陷和回退步骤后，才人工晋级。

以上是后续晋级门槛，不表示 std2 已补做所有新增测试。快充、相机、通话无声的已知缺陷必须继续列出。

## 构建入口

```bash
python3 scripts/fuxi-sources.py prepare
python3 scripts/fuxi-kernel-source.py prepare
sudo scripts/fuxi-build-env.sh image
sudo scripts/fuxi-build-env.sh run bash scripts/fuxi-build-deb.sh <唯一名字>
sudo FUXI_BUILD_ARCH=arm64 scripts/fuxi-build-env.sh image
sudo FUXI_BUILD_ARCH=arm64 scripts/fuxi-build-env.sh run bash scripts/fuxi-ci.sh userspace
sudo FUXI_BUILD_ARCH=arm64 scripts/fuxi-build-env.sh run env FUXI_APT_LOCAL=1 FUXI_APT_SUPPORT_ONLY=1 FUXI_APT_OUT=/src/work/support-apt bash scripts/fuxi-build-pkgs.sh <新版本>
```

源码下载在容器外完成；运行构建容器时禁网。固定 OCI 摘要和 Ubuntu 签名快照固定工具链与依赖，
环境包版本保存在镜像 `/build-environment.lock`，产物保留源码配方和校验和。
支持包可使用 `FUXI_APT_SUPPORT_ONLY=1` 单独构建，不依赖历史 std2/chg3/deb5 二进制。
完整设备源仍只纳入 `packaging/apt/kernels.list` 中验收过的内核；历史二进制不是新版本的构建输入。
不同 CPU 架构各用对应环境；amd64 主机运行 arm64 容器需配置 qemu-user-binfmt。
官方环境使用系统 CA，企业代理环境通过构建 secret 提供主机 CA，不关闭 TLS 或 APT 签名检查。

## 签名与发布

```bash
# 正式签名：使用维护者自己控制的密钥，私钥不入库。
FUXI_SIGNING_KEY=<完整指纹> scripts/fuxi-build-pkgs.sh <新版本>
# 原本 work/apt 是普通目录时，首次迁移加 FUXI_APT_ADOPT=1，旧目录会被归档。
# 仅供本机的 file: 源可显式使用 FUXI_APT_LOCAL=1。
```

构建成功后一次切换 `work/apt` 符号链接；失败保留旧源，旧代际不自动删除。
首次 `--adopt` 普通目录迁移涉及归档目录和创建指针两步；此时掉电可能需要从
`apt.generations/legacy-*` 手动恢复。后续已有指针的快照更新使用原子替换。
新包进入临时目录，先检查包内容、索引、签名，再发布不可变快照。不要直接 rsync 覆盖正在使用的源；
在目标主机使用相同快照发布工具切换指针。本机源明确使用 `file:`；对外源必须使用 `Signed-By`。

客户端公钥必须通过已知可信渠道核对完整指纹，再安装到 `/usr/share/keyrings/`；
不能从未认证的同一个源下载公钥就视为建立信任。密钥撤销/轮换要由旧可信签名或独立渠道公告。
测试生成的密钥只用于测试，不能作为正式项目身份。

默认不打包专有固件；`FUXI_INCLUDE_FIRMWARE=1` 仅用于本地私有源。
第三方许可证和项目权利人授权未核清前，不发布新的对外发行物。详见 `LICENSE.md`、`THIRD_PARTY.md`。
`packaging/release-policy.json` 是公开发布的显式审核门槛；未知状态保持 false，不能由 CI 自动放行。
审核并提交后，运行 `python3 scripts/fuxi-source-bundle.py work/releases/<版本>-sources.tar`，
将对应源码输入、补丁、构建脚本和许可证与二进制一起提供；不能仅提供几个下载链接代替对应源码。
兼容 DTB 权利未核清前，引导镜像仍不可作为新的对外发行物发布。

## 自动检查与人工职责

本机严格检查使用 `bash scripts/fuxi-ci.sh host`。受限沙箱无法创建 Unix socket 时，可显式运行
`bash scripts/fuxi-ci.sh host-restricted` 获取其余测试结果：只有探测到 `EPERM/EACCES` 才跳过真实
GPG 测试，其他签名错误仍失败；CI 禁用受限模式，标准 host 入口清除跳过开关。
有跳过项的结果仅供诊断，不满足完整签名验收或发布门槛。应用测试运行器自行隔离状态目录。

连机迁移前先运行 `bash scripts/fuxi-device-baseline.sh`，检查安装器与仓库 SHA256、服务布局和包版本。
退出码 0 仅表示所检查项目一致，1 表示差异，2 表示证据不足；JSON 内同时保留差异与未知项。
SSH/超时可能返回其他非零码。该工具不调用安装器，不确认启动，不验证启动文件或实际无线功能。
旧合并初始化服务不是放行独立 WiFi/蓝牙检查的理由。迁移必须先保留回退包及条目，再安装支持包、
验证新工具与拆分服务、复核文件校验和及正常启动确认，最后运行完整健康检查；
本轮结果见 [设备收尾验收](设备收尾验收-20261114.md)。手机会过滤 `/usr/share/doc/*`，
因此设备包将 hexagonrpc 来源及许可证保存在 `/usr/share/fuxi-device/hexagonrpc/`，安装后应核对仍在。

每次 main 推送和 PR 自动运行主机回归及第三方源码重建；每周和手动触发定向内核构建、arm64 用户空间构建。
用户空间检查同时构建固定 libssc 0.4.4 矩阵校验候选并运行 C 回归；只生成隔离产物，
不纳入设备支持包、不安装系统库。其 12 项 placement 布局及真实轴向尚未验收，不能自动晋级。
维护检查的 host/kernel job 共享 `work/sources/` 内核原始压缩包缓存，key 随 `kernel/manifest.json` 变化；
`actions/cache` 固定到提交，缓存未命中时仍从固定 URL 下载。命中后依旧验证压缩包 SHA256，
重新解包、应用补丁并校验完整树，不缓存生成源码树、内核输出或固件。
`Full Kernel Package` 保持原有干净计时流程；维护缓存命中不作为编译提速或硬件验收证据。
`Full Kernel Package` 是独立的手动完整打包工作流，使用同一标准构建入口生成 Image.gz、全部已配置 DTB、
模块（启用时）及可安装内核 deb。它不依赖原有定向检查的输出，不复用编译目录或 ccache。
CI 不接手机、不刷写、不持有发布私钥、不自动升级默认内核，不代替上述现场验收。
维护者仍需检查安全公告、审核 CI 结果并维护已知问题。失败的工作流不能作为发布依据。

### 完整包和速度对比

在 Actions 页面选择 `Full Kernel Package`，填唯一内核名（小写字母、数字、点），`jobs=0` 使用 runner 全部可用 CPU。
也可从已经同步的 main 手动触发：

```bash
gh workflow run kernel-package.yml --ref main -f name=<唯一名字> -f jobs=0
```

本地用相同提交、相同内核名和固定容器运行：

```bash
python3 scripts/fuxi-kernel-benchmark.py <相同名字> --jobs 0
```

普通用户 Podman 可用时无需 sudo；Docker 主机可设置 `FUXI_CONTAINER_ENGINE=docker`。
脚本要求已提交的构建配方、至少 8 GiB 空间以及全新输出目录；拒绝覆盖同名产物，不会清理已有构建。
容器中固定 `/src` 路径、amd64 交叉工具链、源码 epoch 和配置，不采用额外实验配置。
`--jobs 0` 对比各机器的实际可用性能；比较相同并行度时，两边都指定 `--jobs 4`。
既有 `fuxi-build-deb.sh` 可通过 `FUXI_BUILD_JOBS` 设置正整数并行度，默认仍为 `nproc`。

`work/benchmarks/<名字>/` 和 Actions artifact 保留以下内容，云端保存 7 天：

- `package/`：内核 deb、config、source、build.json、环境包清单及原包校验和。
- `corresponding-source/`：校验过的 Linux 原始压缩包、该项目提交的完整配方归档及重建说明。
- `benchmark.json`、`summary.md`：CPU、并行数、源码树、提交、环境摘要以及各阶段秒数。
- 阶段日志、成功时的完整编译日志和覆盖全部文件的顶层 `SHA256SUMS`；失败也上传已产生的日志和报告。

下载后在目录内执行 `sha256sum -c SHA256SUMS`。CI 候选未签名、未上机，不等同正式发行物；
不上传固件、兼容 DTB 或引导镜像，不将产物自动发布到 Release/APT。
保留已有文件许可证，正式发行仍遵循前述审核与签名流程。

评估速度时优先比较 `build-package`，它包含全源码校验、配置、编译及 deb 压缩。
`prepare-source` 和 `prepare-environment` 单独计时，其下载/镜像缓存可能冷热不同；
`collect-artifacts` 记录校验与对应源码归档时间。`total_seconds` 不包含 Actions 排队和 artifact 上传，
交付延迟需结合 Actions 的任务时间查看。首次测试结果写入验收记录，不能用定向构建耗时冒充完整构建。
