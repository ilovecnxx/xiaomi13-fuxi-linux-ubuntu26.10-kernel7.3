## (c) 与抓包模块 ID 的对照

【已证实】（logcat `AGM: graph_open` 行 + ACDB SGIT）：
- 抓包 miid 43af/mid 7001024（TX 设备端点）= ACDB SG 0xb0000039 里的 43af/7001024。miid 与 mid 成对一致。
- 抓包 miid 4120/700100e = ACDB SG 0xb000016a 里的 4120/700100e（Handset RX 设备）。
- 抓包 miid 466f/700100f = ACDB SG 0xb0000193 里的 466f/700100f。
- 切换到扬声器后日志出现 miid 4433/700100e，= 别名 272 的 SG 0xb0000002 里的 4433/700100e。
- 所以运行时实例 id（miid）与 ACDB 里的 miid 是同一套静态编号，可以直接拿 ACDB 的 miid 当 SET_CFG 的目标。
- 700100e/700100f：在 ACDB 里都是 RX 设备 SG 的硬件端点，带 HW_EP_MF_CFG(0x08001017)、HW_EP_FRAME_SIZE_FACTOR(0x08001018)、0x0800106a、0x0800113c。日志里 tag 分别为 c0000004（RX）和 c0000005（与 TX 端点 7001024 同 tag）。这两个 mid 内核头文件里没有，名字不详。
- 内核已有 `MODULE_ID_CODEC_DMA_SOURCE=0x07001024`，对得上。

【纠正】`docs/调研-通话音频-Android抓包-20261101.md` 里写的 7001000/7001019/7001005/7001003/7001032 不是语音图的模块。logcat 在 18:39:48.325 同一秒标明它们属于 `GKV Alias 142 StreamRX_PCM_LL_Playback_DeviceRX_Speaker_...`（铃声/提示音流）：ACDB 中它们在 SG 0xb0000023 里（40bd/7001000 WR_SHARED_MEM_EP，40bf/7001005 PCM_DEC，40c0/7001003 PCM_CNV，40c4/7001019，4165/7001032），scenario=1(播放)。语音 TX/RX 图里没有 WR/RD_SHARED_MEM_EP，没有 PCM_DEC/PCM_CNV，也没有 7001019/7001032。语音图的 mid 共有这些（去重）：

## (d) 主线手拼语音子图的最小需求

先说明限制：下面只能确定 ACDB 里这套静态图长什么样；ADSP 固件是否接受缩减版、各端口含义、7001011 等未知模块的作用，ACDB 里没有答案。以下按“能从字节确认”与“推测”分开。

【已证实】的最小骨架（以 TX、RX 各取最短的数据路径）：
1. APM 参数：SUB_GRAPH_CONFIG（scenario=3，perf 与 direction 如上表）、CONTAINER_CONFIG（cap_list 值 0x0b001000/0x0b001001，proc_domain=2，graph_pos 1/3/4，栈大小与 heap_id 见上表）、MODULE_LIST、MODULE_PROP（端口数）、MODULE_CONN。这些参数 id 与 q6apm 已有的 `audioreach.h` 定义一致，说明现有 topology.c 的 token 机制可以表达。
2. 设备端：TX 用 CODEC_DMA_SOURCE(7001024)，参数 0x08001017(12 字节)、0x08001018(4)、0x0800108a(2)、0x08001176(4)；RX 的硬件端点 700100e 需要 0x08001017(12)、0x08001018(4)、0x0800106a(4)、0x0800113c(16)。内核里 CODEC_DMA 的 `PARAM_ID_CODEC_DMA_INTF_CFG=0x08001063` 不在 CSLU/VC 校准里；它出现在未解析的 MTDE 块（字节线索：`00000001 000043ad 08001063`，即 miid 0x43ad 对应 0x08001063），43ad 是扬声器麦 TX 端点（日志 alias 219）。【推测】MTDE/MTDO/MTKT/MTLU 是“按模块 tag/设备”的接口配置块，需要另行解析。
3. VCPM（miid 0x4）：抓包已证实收到 0x080011bc(VSID)、0x08001310、0x0800116b 三个 SET_CFG。ACDB 的语音校准记录里对 miid 0x4 还有一个参数 0x080011ae（8 字节）：流 SG 0x3f/0x40/0x41/0x42 的默认值字节是 `{1,1}`，Fluence 处理 SG 0xb1 是 `{0x14,0x14}`。含义不详【推测：可能是帧长或模式】。
4. 最小模块链（语音 TX）：43af(7001024) → 4147(700101a) → 4167(7001011) → [SG b1：4448(700105a) → 4446/4447(MFC) → 4449(700103c) → 444a(7001028) → 444d(GAIN) → 41fe → 41d3(1000e103) → 48a6 → 4455 → 4456] → [SG 3f 流链]。其中 DATA_LOGGING(700101a) 是可旁路的日志点【推测】，MFC/SAL 是格式/声道转换。
5. 最小模块链（语音 RX）：流 SG 0x40(41b1→41b3→4017→421f→43fc→41b5→41b6) → 0x41(4561→41b7→41b8) → 0x42(4220→4217→4aa5→4216→4012→41c7→4214→420f→41c5→41c3→4205) → 0x43 → 0x2(40cc→4474→418e→4007→4433)。

校准参数在哪些块（【已证实】取得方式）：
- 设备 SG（0x39、0x2、0x16a 等）：CSLU→CDLU→(CDDE, CDDO, POOL)，无键（keyset 为空）的默认记录。例：SG 0x39 的 43af 带 4 个参数，4147/4167 带 DATA_LOGGING 与 0x0800103c。
- 语音 SG（0x3f、0xb1、0x40、0x41、0x42 等）：VCCD→(VCKT 键集, VCDE 组, POOL)。每个 SG 有 2 到 3 个 item：无键默认项，以及按键 0x08001165 或 {0x08001164,0x08001165} 或 {0x08001165,0x080011b5} 区分的项。键的含义不详，VCLU 显示 0x08001165 的取值是采样率 8k/16k/32k/48k【推测：该键即采样率】。同一模块在不同 item 里参数长度可能不同（例：MFC 的 0x08001024 有 8/10/12 字节）。
- 每个模块的参数 id 与长度可直接 `graph 224` / `graph 272` 看，语音 TX 流 SG 的 41aa/700101b 是 6 个参数（0x08001035/36/37/38/39/3d），41d3 是 10 个（0x1000e000..09，共约 436 字节），4289/SAL 有 0x08001050(36 字节)。
- 参数本体的字节在 POOL 里，偏移由 CDDO/VCCD 给出；`cal_for_sg()` 目前只返回长度。导出具体数值需要小改，不是格式问题。

## (e) 还缺什么

2. SG 之间的数据连接：blob 里没有直接写出，只有 A 记录的邻接线索和外部端点引用；4167:b>4021:2、418e:19>467e:4 这类“指向别的 SG”的引用意义只能靠推测。
3. 语音校准键的语义：0x08001164/65/66/67/b5/b6 及 VCMK/VCLU 的表结构未解析，不能确定“某个 VSID/网络/采样率”应选哪个 item。
4. 0x08001162、0x08001061 的字段含义，以及 SG 头里的 0x08000001/0x08000010。
5. 运行时没有拿到的 GRAPH_OPEN 本体（共享内存，strace 看不到）。ACDB 给出的是图定义，AGM 实际拼接时可能增删模块。想确认就得抓 GPR 共享内存内容或在 Android 里读 AGM 的 graph dump，那需要连手机，这次不做。
6. 700100e/700100f 的名字。它们和 CODEC_DMA_SINK(7001023) 不是同一个 mid，但 SG 0xb0000053 里 7001023 和 7001011 并存，说明同类端点有多种实现；实际硬件走 MI2S/TDM 还是 CODEC DMA 要看 DTS，日志里出现过 `TDM-LPAIF-RX-SECONDARY`。
7. SG 0xb0000193 对应的运行场景（GKV `d7000001`）未查明。

## (f) MTDE/MTDO 补充解析（11-01 晚，主机离线，只读）
- 【已证实，字节级】MTDE（偏移 0x32822，5528 字节）= 连续记录 `[count][(miid, param_id)×count]`，共 412 条，恰好用完整块。count 取值只有 1、2、10。
- 【已证实】0x43ad（扬声器麦 TX 端点，记录 4）和 0x43af（TX 设备端点，记录 99）都登记了 `0x08001063`（CODEC_DMA INTF_CFG）；0x4120、0x4433（RX 设备端点）登记的是 `0x0800101b`，不是 INTF_CFG。全表 INTF_CFG 共 15 处。
- MTDE 只列「某 miid 有哪些参数」，**不含参数值**。
- 【已证实，否定】MTDO（偏移 0x33dc2，856 字节）不是 `(count, 偏移)` 的 8 字节定宽对：按此读法 count 列里混有 0x1fa… 这类偏移，说明它是变长结构。其中有些偏移确实指向 POOL（按 POOL 起点读出整齐数据，按文件起点读出乱码）。MTDE 记录到 MTDO 条目的对应关系**未解析**，INTF_CFG 的具体数值（lpaif_type、hw_interface_idx、声道数）仍未拿到。
- 不要再按定宽读 MTDO。下一步候选：对照 MTLU（4554 个 u32，开头像嵌套的 `(id, 偏移)` 层级表）和 MTKT（`miid-count, b0000001, c0000006…` 看起来是 SG→容器键表）推断 MTDO 的游标；或者放弃 ACDB，直接用 Android 侧已抓到的 GPR 包取 INTF_CFG 值（抓包文档里 GRAPH_OPEN 本体在共享内存，拿不到，但 SET_CFG 类的包可能含 0x08001063）。
