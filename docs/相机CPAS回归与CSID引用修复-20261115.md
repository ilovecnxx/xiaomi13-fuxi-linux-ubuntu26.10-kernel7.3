# CPAS 故障回归与 CSID 父引用修复（2026-11-15）

继续 `cam8icp` 之后的共享资源审查，新增隔离的
[cpas-tests 配方](../kernel/experiments/camera/cpas-tests/README.md)。
本轮修复 CSID 上电失败后的父引用泄漏，并为实际 CPAS 诊断函数增加故障和并发回归。
没有实现 Q-channel 停机握手，不宣称 MM0 已修复，也没有生成或安装新的手机内核包。

## CSID 修复

`csid_set_power()` 先调用 `parent_dev_ops->get()`，随后获取 CAMSS runtime PM、
regulator 和时钟，并执行复位。原先父设备获取成功后，五个后续步骤中的任一步失败，
都会直接返回而没有匹配的父 `put()`。对于使用 VFE 父设备的路径，这会留下 VFE
引用；反复失败还会累积。正常关机已有父 `put()`，不能据此认为失败分支也已处理。

补丁按资源获取顺序反向清理：复位失败先关 IRQ/时钟，再释放 regulator、runtime PM
和父引用；较早的失败从相应标签进入。父获取自身失败时不调用 `put()`，保留原始
上电错误，不用清理返回值覆盖它。原有正常上电与关机路径保持原样。

三个 KUnit 测试直接调用实际 `csid_set_power()`，用计数父设备和真实 runtime PM
核心验证父获取失败、PM 未启用时连续三次失败，以及 resume 回调返回超时。
检查返回错误、父获取/释放次数以及 runtime PM 使用计数。测试没有实际上电 VFE，
也没有分别注入 regulator、时钟和复位错误，不能扩称为全部硬件失败路径通过。

## CPAS 诊断测试

十四个参数化案例直接运行 `camss_cpas_snapshot()`，没有复制诊断算法。寄存器由内存
模拟，ICP 使用实际 common-clock 框架注册的测试时钟，只有测试时钟模拟状态响应。

- 无映射、无可选时钟、camera/CPAS 版本不匹配、control 为 0 或包含额外位时跳过。
- 时钟 prepare 和 enable 分别失败；验证只释放已取得的资源，并能继续下一次采样。
- 四种 phase 标签下成功采样；标签测试不等于执行了真实 VFE 复位或停止路径。
- 只有 QDENY、没有 QACCEPTN 时等待实际 10 ms 超时，再验证后续成功采样。
- 两个 VFE 调用线程各执行八次采样，检查 16 次独立的时钟获取/释放。
- 每例检查时钟未保持 prepared/enabled、互斥锁可再次获取，以及整个模拟寄存器窗口
  未发生非预期写入。测试线程全部退出后才释放时钟和夹具。

这些测试只验证诊断窗口串行化，不证明整个 CPAS 子系统空闲。probe lookup/defer
未在测试中执行；模拟寄存器也不验证真实总线、硬件状态新鲜度或供电时序。

## 验证结果

- x86_64 QEMU/KASAN、mutex debugging：CPAS 14 项、CSID 3 项通过。
- 反例验证：临时恢复 runtime PM 获取失败后的直接返回，CSID 三项中两项因父
  `put()` 缺失而失败；恢复修复后，最终完整 17 项全部通过。
- ARM64 GCC 15.3，`W=1 drivers/media/platform/qcom/camss/` 编译通过，无警告；
  手机配置未启用新增 KUnit 测试。未构建完整内核包，未修改 DT。
- 环境解除限制后，严格 `bash scripts/fuxi-ci.sh host` 通过：366 项脚本测试、
  62 项 SuperTerm 测试，无跳过。此前受限运行曾跳过一项 GPG socket 测试，
  最终以严格回归结果为准。
- 两份补丁从固定父提交重放，结果树为
  `6cd804d46058493551e8549948a270b3381dec38`，与已测试源码一致；父清单、
  补丁及配置 SHA256 均记录在实验 `manifest.json`。
- `checkpatch.pl --no-signoff`：零错误，每份补丁各一条新增文件的 MAINTAINERS
  提示；现有 `QUALCOMM CAMERA SUBSYSTEM DRIVER` 条目已覆盖该目录。
  本地实验没有添加未经确认的 DCO 签字，不表示已满足上游投稿要求。

## 本轮设备复查

最初 SSH 受 socket 限制阻挡；环境解除限制后，使用已固定主机密钥的严格 SSH
完成只读基线及健康检查。运行与默认均为 `7.4.0-rc1-fuxi-deb9`，回退为 deb8；
安装器哈希与仓库一致，`pending/tries/once` 均为 0，无 D 状态进程和失败服务。
本轮没有安装候选、重启手机或启动相机。

无线 HTTPS、管制域及传感器检查通过，但整体验收有 **2 项失败**：蓝牙
`Powered: no`，后续确认 `Soft blocked: yes`、`Hard blocked: no`；Phosh 当前
active，但 `NRestarts=1`，日志记录重试发生在手机时间 08:46:54 CST。
这些是现有 deb9 的状态，不能归因于未安装的候选，也不能沿用上一轮“健康失败 0”
作为当前结果。未更改蓝牙开关或重启桌面。传感器矩阵回退、陀螺仪单位和轴向等
原有验收限制仍然存在。原始日志仅保留在本地 `work/camera-cpas-tests-20261115/`。

## 共享资源审查与下一步

固定父树 `9f78c9163e7fce86fb1ba627a9b0380899da1156` 中：

| 路径 | 观察与约束 |
| --- | --- |
| `camss-vfe.c:vfe_put()` | 关闭 VFE 时钟后才释放 CAMSS runtime PM；在 runtime suspend 尾部直接增加 CPAS 寄存器操作没有足够的时钟持有证明 |
| `camss-csid.c:csid_set_power()` | 同时持有父 VFE 和独立 CAMSS PM 引用；本轮修复后续失败的父引用泄漏 |
| `camss-csiphy.c:csiphy_set_power_legacy()` | 自己持有 CAMSS PM 引用；不能仅用 VFE 的 power_count 判断全局空闲 |
| `camss-tpg.c:tpg_set_power()` | 也是 CAMSS PM 使用者；需纳入共享资源设计 |
| `camss.c:camss_runtime_resume/suspend()` | HF 与带宽投票位于共享 PM 回调；逐路径设置带宽时失败不会完整撤回此前成功的其他路径 |
| `icc-rpmh.c:qcom_icc_set()` | 丢弃 `qcom_icc_bcm_voter_commit()` 的错误并返回 0，消费者看不到底层失败 |
| `interconnect/core.c:icc_set_bw()` | provider 返回错误时会重提旧带宽，且不检查这次提交的错误；软件数值恢复不证明硬件投票恢复 |

下一步需要设计共享 CPAS 时钟/电源的持有范围、全局使用者与启动对称性，再接入停机
握手。错误处理必须考虑尚未完成的 RPMh 请求、旧投票重提及跨路径回滚，不能简单地
透传 provider 错误后关掉时钟。正式握手前仍需补充实际设备的故障分支、第二次启流
与恢复验收；现有候选继续留在实验目录。
