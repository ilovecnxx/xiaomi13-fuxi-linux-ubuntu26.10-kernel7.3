# 相机 HF 时钟时序实验（2026-11-12）

后续进展（2026-11-14）：libcamera 首帧初始化候选已完成原生构建、GDB
对照及六轮重复采集，见[首帧修复验收](相机首帧修复验收-20261114.md)。
该软件修复不改变本文对 MM0 根因尚未确定的结论；以下保留当时实验记录。

## 依据与假设

Android 恢复后继续分析本地主机保存的 cam5diag 日志。没有把清除 BCB
命令后的正常启动解释为相机修复；上次清除授权仅适用于那次恢复。

`trace-gdb.log` 中 MM0 的三次启流批次，六条命令的地址、data 和 wait
完全相同，分别为：

| 开始时间（秒） | 结果 | 耗时 |
| --- | --- | --- |
| 395.160858 | 有匹配 TCS 完成事件 | 51 微秒 |
| 430.453891 | 有匹配 TCS 完成事件 | 44 微秒 |
| 441.121049 | 无匹配完成，随后超时快照 MM0 未完成 | 超过 10 秒 |

两次撤销 MM0 投票也有完成事件，分别为 399.291211（111 微秒）和
440.616842（445 微秒）。这些对照不支持“该投票数值总会失败”，但不能排除
硬件状态、并发和掉电时序影响。日志完整性限制仍沿用原诊断报告。

源码顺序：`vfe_get()` 调用 CAMSS runtime resume 后才设置并启用 VFE
时钟；`vfe_put()` 先关 VFE 时钟，再调用 CAMSS runtime suspend。
CAMSS 的两个回调分别申请和撤销 ICC 带宽。SM8550 原先没有 `pm_clks`，
`gcc_axi_hf` 只在 VFE 时钟表里，因此带宽转换时不能依靠 VFE 的引用保持
HF 门控打开。尚未证明这一时序就是 MM0 不响应的根因。

## 隔离候选

`cam6hfclk` 基于 cam5diag，只在 SM8550 的资源表增加
`.pm_clks = { "gcc_axi_hf" }`。复用现有运行时 PM 时钟接口，在申请带宽
前开 HF 门控，撤销带宽后关门控，保留 VFE 自己的时钟引用和所有原有投票。
不改频率、电源域、DTB 或 RPMh 协议，也不尝试强制回收超时 TCS。

配方位于 `kernel/experiments/camera/hfclk/`，结果树
`6fce8068ea12f794d28ee05b6883c4a478ad1604`，源码提交
`c539e8aaf80f3ccc1ce57bfc6888007020c8ce45`。标准内核配方保持原样。

另确认 `qcom_icc_set()` 丢弃 voter 的错误返回，但本候选不混入错误传播修改：
超时后请求仍被控制器引用，返回错误后自动回滚也可能再次等待同一资源，需与
请求生命周期及有界等待一起设计，不能单独宣称已解决故障恢复。

## 实机结果

通过 `adb reboot recovery` 从 Android 进入 deb9。基线启动文件校验通过，
启动计数清零，无持续 D 状态线程、失败服务或存储错误。手机现有安装工具
没有 `verify` 子命令，使用各条目的 `SHA256SUMS` 做直接校验。

只安装 Linux deb，临时配置选择 OV13B10 DTB，安装完成后删除临时配置。
cam6hfclk、deb9、deb8 三条目校验通过；新旧相机候选的实装 DTB 哈希相同。
正常重启进入 cam6hfclk，启动已确认；采集前预置下次默认 deb9、回退 deb8。

| 测试 | 结果 |
| --- | --- |
| RAW 2104×1560，5 帧 | 完成，正常退出 |
| 第 1–4 轮：半尺寸 CPU 300 帧 → 全尺寸 CPU 120 帧 | 四轮均完成并正常退出 |
| 第 5 轮：空闲约 67 秒后半尺寸 CPU 300 帧 | 完成，正常退出 |
| 第 5 轮：全尺寸 CPU 120 帧 | 出帧前数组越界断言，退出码 134，停止测试 |

全尺寸请求 4208×3120，由 libcamera 调整为 4200×3120 ABGR8888。
断言为 GCC 15 `std::array<double, 1024>::operator[]` 的
`__n < this->size()`，与 cam5diag 曾记录的用户态故障一致。
设备没有 `coredumpctl` 和 `/proc/sys/kernel/core_pattern`，此次无法取得 core
或崩溃栈；未为复现断言继续采集。其与 RPMh 故障的关系仍未确定。

本轮没有 RPMh batch 超时、AMC 错误、存储错误或持续 D 状态线程。
包括断言退出在内，CAMSS 均恢复为 suspended，HF 门控 enable count 为 0。
这些结果只支持候选在本轮条件下未复现 MM0 阻塞，不构成相机功能验收。

## 跟踪证据与限制

首轮 `trace_pipe` 经 SSH 流读取在约 68.9 秒返回 `Bad address`；此前文本中
也有截断行。因此首轮流不能用于完整的 RPMh 配对结论。停跟踪后读取剩余
`trace` 缓冲，保留了首轮全尺寸采集。该完整区间从 69 秒起有 7547 个完成
批次，无未配对批次或配对异常。

第 2–5 轮改为每轮清空缓冲、开启跟踪、限时采集、关闭跟踪并保存静态快照。
四轮的所有 CPU overrun、commit overrun、dropped events 均为 0。离线审计：

| 轮次 | RPMh 完成批次 | 未完成批次 | 配对异常 |
| --- | --- | --- | --- |
| 2 | 3837 | 0 | 0 |
| 3 | 5321 | 0 | 0 |
| 4 | 3839 | 0 | 0 |
| 5 | 3037 | 0 | 0 |

四轮共 8 个 HF 开关窗口内，CAMSS 的全部 ICC 申请和撤销事件都发生在
`clk_enable_complete` 与 `clk_disable` 之间，包含失败采集的退出清理。
例如第 2 轮全尺寸：HF 开启完成 199.584851 秒，最后 ICC 撤销返回
203.702685 秒，HF 关闭 203.702689 秒。8 次 CAMSS resume 为
0.122–3.600 毫秒，没有之前超过 10 秒后仍返回成功的情况。

仍有重要对照限制：本轮 MM0 启流 data 为 `0x6233c9cf`，撤票后为
`0x60f9c3be`；之前故障记录分别为 `0x6139c9cf` 与 `0x40000000`。
候选没有更改带宽表或 DT，但运行时聚合投票状态不同，不能把本轮未复现
直接归因于 HF 修改。后续需对齐显示/其他互连消费者状态，再验证相同
MM0 投票及系统挂起恢复；本轮只覆盖 CAMSS runtime suspend 和空闲等待。

原始日志、实验脚本与离线分析在 `work/camera-hfclk-20261112/`，不提交。
候选仍隔离于标准配方和 APT 发布清单之外。

## 双系统状态

本轮 `adb reboot recovery` 后只读检查发现 BCB command 再次为
`boot-recovery`。没有再次清除，先前授权仅用于上次恢复。测试结束后选择
正常 Linux recovery 重启回 deb9；回退 deb8 保留。进入 Android 的行为
仍需结合此 BCB 状态处理，不能承诺普通重启会返回 Android。

已实机确认回到 deb9，默认 deb9、回退 deb8；两条目启动文件校验通过，
pending/tries/once 均为 0，无失败系统服务。第一次查询见两个 cpufreq
线程短暂等待 RPMh/ICC，后续复查 D 状态线程为空，也没有 RPMh 超时或
存储错误，不能把瞬时等待记成复现。实验内核保留安装但不作为默认。
