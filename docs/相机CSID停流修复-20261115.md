# CSID 停流修复（2026-11-15）

继续从 cam9pm 的 CPAS 握手源码向前开发，不回退旧源码。
cam9pm 的两轮 RAW 启停通过，但 RGB 60 帧后 CPAS status=0x5 停机超时，
现场日志已保存，见[握手记录](相机CPAS运行时握手-20261115.md)。

## 已确认的软件缺口

`csid_set_stream()` 仅在 `phy.need_vc_update` 为真时调用硬件配置。
启动会清除此标志；正常采集期间链接不变，停止也被同一条件跳过。
修复后停止不受配置脏标志限制，并将标志重新置位，使后续启动重配。
没有改变 CPAS 超时判断或关闭故障锁定。

新增回归直接调用生产函数，使用计数硬件回调执行 20 次启停。
原逻辑只调用一次启动、零次停止，测试失败；修复后正常启停 20 次。
包括既有 CPAS 和 CSID 故障测试共 32 项 QEMU/KASAN 测试通过，零跳过；
ARM64 `W=1 drivers/media/platform/qcom/camss/` 通过，无警告。

这是软件路径证据，还不能证明硬件已经排空。VFE gen3 的 global_reset/halt
没有实际硬件重置/排空动作；CSID 停止配置是否足够，需要实机检查。
首期仅验收 OV13B10 单路径，不宣称独立多 VC 并发启停可用。

## 实机结果

正常安装和重启通过，运行/默认 cam10stop，回退入口 deb9；启动计数清零，
无失败服务，probe CPAS 启停成功。没有回退到旧版。

普通用户使用同一补丁 libcamera 客户端完成 RGB 2104×1560 60 帧，错误/无效帧
均为零，EGL context 创建/销毁各一次。但停止后 CPAS status 仍为 `0x5`，
10 ms 超时，runtime PM 进入 error。因此停止验收仍失败，已停止追加采集，
现场保存在 `work/camera-cpas-pm-20261115/cam10-rgb-stop-failure-state.log`。

该结果证明修复漏掉的软件停止回调仍不足以排空硬件，不能把它写成 MM0 修复。
下一步核对原厂 IFE/CSID 停止确认、复位和时钟顺序，保留当前源码改进继续推进。
