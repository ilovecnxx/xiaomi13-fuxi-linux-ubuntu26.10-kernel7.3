## 候选与验证

cam12order 将 CPAS 路径的共享时钟和启动握手移到带宽请求之前，传感器/DMA
仍在 runtime resume 成功后才开始。旧 DT 无 CPAS 路径的顺序保持不变。
带宽错误时先停止空闲 CPAS，再撤销已成功的请求并清理时钟引用，保留原错误。
清理握手失败另记错误；这不是实际 RPMh 超时后的恢复保证。

`edfabc4cd0cf8c50b5578e85db8487b9080e17e8`。配方见
[cpas-order](../kernel/experiments/camera/cpas-order/README.md)。

  检查（20 次启停）和第二条带宽请求失败后的引用/投票清理检查。
- ARM64 `W=1 drivers/media/platform/qcom/camss/` 编译通过，无警告。

测试中的带宽返回值由桩提供，没有仿真 ICC provider、GDSC 或真实在途请求。
共享时钟提前启用是否足以解决 MM0 必须实测；下述实机结果已证明该改动不足以修复重开。
`qcom_icc_set()` 吞掉 BCM 错误、ICC core 失败后重提旧投票的问题仍保留，
需要单独的错误传播和失败状态验证，不能只改一个返回值后宣称恢复安全。

cam12order 正常启动、Phosh active，自动确认 `pending=0 tries=0 once=0`。
运行及默认均为 cam12order，恢复入口仍为 deb9，没有例行回退。

| 检查 | 实际结果 |
| --- | --- |

关键单调时间：

- 107.914798：两轮客户端首次 CPAS start 成功。
- 110.075011：首轮 CPAS stop，status=0、result=0。
- 110.088722：第二轮 CPAS start，status=1、result=0。
- 120.301962：RPMh batch 0 的六条命令超时；MM0 `0x50030`、data `0x6139c9cf`，

- 120.310715：驱动仍继续 reset-done；ICC provider 吞掉 BCM 错误的问题仍存在。

不能通过永久保电、删除 MM0 投票或跳过响应来认定完成。
