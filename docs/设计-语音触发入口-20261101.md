## 1. 结论
- 在 `q6apm-dai.c` 的 `q6apm_fe_dai_component` 上加一个枚举控件 `Voice Call`，取值 `Off / SIM1 / SIM2`，put 回调调用 `q6apm_voice_start/stop`。
- 枚举而不是整数 VSID：内核只会把两个已知 VSID（SIM1 `0x11c05000`、SIM2 `0x11dc5000`）发给 ADSP，用户态给不出任意值。
- 用户态入口：`amixer cset name='Voice Call' SIM2`，也可写进 UCM Voice verb 的 EnableSequence。

## 2. 为什么挂在 q6apm-dai 组件上（已核对）
- `q6apm_voice_start(dev, …)` 用 `dev_get_drvdata(dev->parent)` 取 `struct q6apm`（q6apm-voice.c:238，q6apm.c:721 同样写法）。
- `q6apm_audio_component` 注册在 GPR 设备自己身上（q6apm.c:888 `snd_soc_register_component(dev=&gdev->dev…)`），它的 parent 是 GPR 总线设备，drvdata 不是 `struct q6apm`。挂在这里会解引用错误的指针。
- `q6apm-dais` 由 `of_platform_populate(dev->of_node, NULL, NULL, dev)` 建成 gdev->dev 的子设备（q6apm.c:894），`component->dev->parent == &gdev->dev`，drvdata 正好是 `struct q6apm`。所以控件的 `component->dev` 可直接传给 `q6apm_voice_start()`。
- `q6apm_fe_dai_component`（q6apm-dai.c:1004）目前没有 `.controls`；FE dai-link 的 cpu 是 `q6apmdai`，控件会出现在声卡上。

## 3. 控件语义
| 当前 | 写入 | 行为 |
|---|---|---|
| Off | SIM1/SIM2 | `q6apm_voice_start(dev, vsid)`，成功返回 1（值变化） |
| SIMx | 同值 | 返回 0，不动 ADSP |
| SIMx | 另一张卡 | `-EBUSY`，必须先写 Off |
| SIMx | Off | `q6apm_voice_stop(dev)`，返回 1 |
| 任意 | 实验开关为 0 | `-EOPNOTSUPP`（`q6apm_voice_start` 已有这个检查，q6apm-voice.c:242） |

- get：返回当前选中项。需要把 `q6voice_active` 改成 `q6voice_cur_vsid`（0 表示未运行），在 `q6voice_lock` 下读写，并导出 `q6apm_voice_get_vsid()`。
- 实验开关：现在是 `0444` 的 module_param，内建（`CONFIG_SND_SOC_QDSP6_APM=y`）时只能走 cmdline `snd_q6apm.voice_experimental=1`（KBUILD_MODNAME 已核对为 `snd_q6apm`），而 cmdline 烧在 DTB 的 `/chosen/bootargs` 里（scripts/fuxi-build-abl.sh:106），改它要重编 DTB。建议改成 `0644`，上机后 `echo 1 > /sys/module/snd_q6apm/parameters/voice_experimental` 再开，默认仍为 0。
- 控件始终注册，不按开关条件注册：这样 get/put 的行为恒定，没开开关时只是返回 -EOPNOTSUPP。

static int q6apm_voice_ctl_put(struct snd_kcontrol *kc, struct snd_ctl_elem_value *uc)
{
	struct snd_soc_component *c = snd_kcontrol_chip(kc);
	unsigned int sel = uc->value.enumerated.item[0];

		return 0;

## 5. 生命周期与风险
- 卸载/关机：在 `q6apm_dai_probe` 里加 `devm_add_action_or_reset()`，调用 `q6apm_voice_stop()`，避免组件消失后图还开着。
- 阻塞时间：put 在 ioctl 里同步等 ADSP，每条命令最长 5 秒（audioreach.c:632）。一次 start 约 12 条命令，ADSP 不响应时最坏约 1 分钟。可接受，因为是实验入口；正式版应放到工作队列。
- ADSP 重启（SSR）后图会失效，`q6voice_cur_vsid` 仍非 0。恢复办法：写 Off 再写 SIMx；`q6apm_voice_stop()` 忽略命令失败继续释放内存（q6apm-voice.c:337-346 已是这样）。SSR 自动清状态未做。
- `q6apm.c:577` 对 `graph->cb` 无 NULL 检查，语音图传 `cb=NULL`。只在 SH_MEM watermark 事件触发，语音图没有共享内存端点，实际走不到；顺手加一个 NULL 检查更稳【推测：不会触发】。

## 6. 控件解决不了的问题（要在上机前想清楚）
1. **codec 侧不会上电**【推测】。WCD 播放/采集是 BE dai-link（sm8550-xiaomi-fuxi-audio2.dtsi:60,76），ASoC 只在 FE 流驱动下才给 swr/RX 宏/WCD 上电。kcontrol 只让 ADSP 起图，不会触发 DAPM。第一次上机只能验证「ADSP 接不接受 GRAPH_OPEN，各命令返回码」，不会有声音。要出声需要另一个机制（例如一个哑 FE 经 DPCM 连到 WCD BE），本文没设计。
2. **同一硬件接口被两个图占用**【推测】。试验期间不要同时开普通 WCD 播放/采集（BE 图用同一个 RX_CODEC_DMA_RX_0 / TX_CODEC_DMA_TX_3）。
3. **INTF_CFG 的缺口比 TASKS 写的小一点**（新发现，读源码得出）。主线下发 `PARAM_ID_CODEC_DMA_INTF_CFG (0x08001063)` 时，三个字段来自 `lpaif_type`（1=RXTX、2=WSA、3=VA、4=AXI）、`intf_index`（RX0/TX0=1，RX1/TX1=2，依此类推）和通道掩码（audioreach.h:767-780，audioreach.c:766-776 区域，lpaif_type 赋值在 769）。所以格式已知，取值是小整数。按 fuxi 的 WCD 链路，RX_CODEC_DMA_RX_0 应是 {1,1,mask}，TX_CODEC_DMA_TX_3 应是 {1,4,mask}【推测：Android 是否真用这些、通道掩码是多少，未验证】。另外语音图的端点模块（0x0700100e 等）和主线的 CODEC_DMA 模块不是同一个 id，参数 id 也不同（0x0800106a/0x0800113c、0x0800108a/0x08001176），所以不能直接套用主线的下发函数。「ACDB 离线拿不到数值」这条结论仍成立，只是现在知道可以猜，不必再抓包才能起步。
4. 触发源（MM 来电/拨号状态 → 写控件）没设计。ModemManager 的音频端口信息和 UCM 都还没看。

### 7c. 第 3 个图（GPR 端口 0x2011）离线分析（2026-11-01，未上机）
- 【已证实】`fuxi-acdb-dump.py sg 0xb0000193`：模块 466f(700100f)、4825(700101a DATA_LOGGING)、4862(7001011)。466f 登记 0x08001017/0x08001018/0x0800106a/0x0800108a/0x0800113c，抓包 #130/#132 下发的是 0x08001017 `{48000, 0x20018, 1}` 和 0x0800101b `{0,1,0x10001,3,0x200004,1,1}`，随后 PREPARE/START。
- 【已证实】4862 的 11 号输出是 TX 图的回声参考输入：`4862:11>4448:4`（TX 图 conns 里列为 graph-external，本实现未发送）。ACDB 文档 §(a) 也把 4862 归在 SG 0xb0000193。
- 【推测】因此 0x2011 是“回声参考用的 RX 设备图”，一个 SG、3 个模块，不含 VCPM 相关内容；它不是 VCPM 接受 VSID 的前提，只是给 TX 图的 4448:4 提供参考。补它大概率不会让 EBADPARAM 消失，但通话要有回声消除就需要它。
- 【已证实，抓包序号】VCPM VSID(#186)之前，0x2012/0x2013 都已 OPEN、做过一次 out-of-band SET_CFG(16 B，共享内存里的校准)，并发过 0x01001008(带外大负载命令，**不是 REGISTER_MODULE_EVENTS**；0x2012 三次、0x2013 两次)；还做过 MAP(0x2002)。我们的实现这几步都没有：没有校准 SET_CFG，没有 0x01001008，没有 SHARED_MEM_MAP。这是比第 3 个图更像 EBADPARAM 原因的差异【推测】。
- 【缺口】`sg` 子命令不给 SG 内的连线。0xb0000193 的 4862→4825/466f 连线要从 GKVL 里 `0xd7000000=0xd7000001` 那条的 B 记录读；工具暂不支持按 GKV 取图。
- 0x0800101b（28 B）在内核头文件里没有定义，ACDB 里只在 4120/4433/466f 这类 RX 设备端点登记【已证实】，含义未知。
- 下一步候选（离线）：(1) 给 acdb-dump 加按 GKV 取图；(2) 弄清 0x01001008 是什么命令并决定是否实现（见 §7d）。

### 7e. 0x01001008 带外负载抓到了（2026-11-02 00:15，Android 上机）
- 方法：`scripts/fuxi-gpr-shmdump.c`（ptrace 附着 `android.hardware.audio.service`，拦截它对 fd 8 `/dev/aud_pasthru_adsp` 的 write；遇到 0x01001008/0x0100100c 时，用 `pidfd_getfd` 复制目标进程里同一个 dmabuf 并自己 mmap 读出）。只读，不改目标进程；两次附着后 HAL 都正常脱离（TracerPid 0）。拨号用 `scripts/fuxi-android-dial-sim2.sh`，已验证走卡 2（电信），挂断后 `mCallState=0`。
- 数据：`work/claude-logs/android-voice-shmdump2-20261102/`（`packets.log` + 41 个共享内存转存，0 个读失败；含 `pkt*-op01001008-map*.bin`）。第一次抓的 `android-voice-shmdump-20261102/` 里共享内存读取全部失败（process_vm_readv=-1），只有 `packets.log` 可用。这两个目录都在 `.gitignore` 的 `work/*` 下，不会进库。
- 【已实测】0x01001008 共 7 个：0x2012 四个（#111 #114 #117 #620）、0x2013 三个（#141 #147 #606）。GPR 负载 16 B = `{偏移 lsw, msw=0, 共享内存地址 handle, 大小}`，与此前 strace 看到的一致。每个之前有一次 0x0100100c（MAP），通话结束后有对应 0x0100100d（UNMAP，负载就是那个 handle）。
- 【已实测】共享内存里从 `lsw` 开始是一个 16 B 头 `{miid=4, param=0x08001163, size, err=0}` 加 `size` 字节数据，即一个带外 SET_CFG。param 0x08001163 与 ACDB 的 `VCCD` 块头是同一个 ID（`fuxi-acdb-dump.py cal_records_vc`）。
- 【已实测】数据格式：`[1][sg][record_len][record]`，后面接一串 `{len, n, param_id...}`（首个 param 多为 0x08001165）。7 个块的 SG 依次是 0xb00001d9、0xb0000041、0xb0000040、0xb000003f、0xb00000b1、0xb00000af、0xb0000042，每个都在 ACDB 的 VCCD 里能找到同一个 SG。
- 【已实测】**不是 ACDB 的原样拷贝**：整块在 `Tutu_acdb_cal.acdb` 里搜不到；同 SG 的 record 与 VCCD 里的记录长度不同（#111：Android 2984 B，ACDB 1900 B，1223 个字节不同）。结构相似（键值数、项数相同位置），但内部偏移与长度字段不同。
- 【推测】Android 运行时按当前键值（设备、网络、VSID 等）从 VCCD/VCDE/VCLU 组装出这块，所以不能靠"拷 ACDB 默认块"。这也说明此前"默认校准总量"对不上大小是预期结果。
- 【未知】这 7 个块是否是 VCPM 接受 VSID 的前提；抓到的顺序里 VSID 之前确实发过它们，但"缺它们就 EBADPARAM"仍是推测。
- 下一步候选（均需用户确认）：(1) 用抓到的块原样重放做一次实验（需要在内核里分配 dma-buf、发 MAP/SET_CFG/UNMAP，只对 SIM2 的 VSID 有效）；(2) 逆向 VCCD → 运行时格式的映射，工作量大；(3) ADSP 侧 ftrace 看 APM 为什么拒 VSID。

### 7f. 重放实验：抓到的带外块被 ADSP 全部拒绝（2026-11-02 00:38，#229）

### 7g. Android GRAPH_OPEN 与我们的图逐项对比（2026-11-02，离线）
- 工具：`scripts/fuxi-graphopen-parse.py`（`dump/json/cmp`；记录链必须恰好吃完 size）。输入：0x2012 = `pkt0104-op01001006-map0-7703003000.bin` 偏移 0x1000 大小 0xdf0（31 条记录）；0x2013 = `pkt0138-op01001006-map1-7703003000.bin` 偏移 0x1000 大小 0xdd8（#136 的块在 #138 的转存里，map1）。我们的图：`q6voice-graphs.h`。
- 【已实测】**0x2013（TX）与我们的 TX 图（别名 224）SG、容器、32 个模块（mid/容器/端口数）完全相同**；34 条图内连线相同。Android 多 8 条跨图连线（如 `4862:11>4448:4`、`4167:11>4021:2`），我们按设计不发。
- 【已实测】**0x2012（RX）与我们的 RX 图不同**：共有 SG 只有 0xb0000040/41；Android 另有 0xb0000045、0xb00001d9（听筒链路），我们另有 0xb0000002/42/43（别名 272 扬声器）。
- 【已实测，关键差异】Android 的 GRAPH_OPEN 里还有两类记录，**我们完全没发**：
  - `miid 4（VCPM）param 0x08001162`：每个语音 SG 一条，`{n=1, sg, nprops=1, 0x080011b2: [cnt]{vcpm_param_id, miid}}`。TX：SG 0xb000003f → `0x8001177→41ae, 0x8001178→41b0, 0x800117a→41ab, 0x80011e1→41ac`；SG 0xb00000b1 → `0x80011ad→4449`。RX：SG 0xb0000040 → `0x800117b→41b3, 0x800117c→41b1, 0x800117e→41b6, 0x80011e2→41b5, 0x80011e3→43fc`。即 GRAPH_OPEN 时告诉 VCPM「这个 SG 里哪个模块担任哪个语音角色」。
  - `miid 1（APM）param 0x08001061`：模块控制链路（`{n, {src, src_ctrl_port, dst, dst_ctrl_port, 2 props: 0x8001062 {1, intent_id}, 0x800136f {1}}}`），如 `41b0:c0000001>4287:c0000001`（intent 0x8001207）、`4654:c0000003>41b0:80000002`。
- 【已实测】这两类内容 **ACDB 里原样就有**：`fuxi-acdb-dump.py graph 224/272 --json --no-cal` 的 `x162_unparsed` 与 `ctrl_links`，与 Android 下发的逐项一致（TX 两个 SG、RX 的 0xb0000040）。不需要运行时组装，可离线生成。
- 其他小差异【已实测】：Android SG 多发属性 0x080010cc（=-1）；容器多发 0x080010cb（parent=-1）、0x08001174（heap_id，e0000045 为 2）、0x0800124d。我们只发 3 个 SG 属性、4 个容器属性。
- 【推测，最强候选】VSID 被 EBADPARAM 的原因：VCPM 收到 VSID 时没有任何 SG 向它注册过语音模块（0x08001162 缺失），找不到要绑定的会话。这也可解释 #229 重放的块被回 status 1（块的 miid 4 / param 0x08001163 是给 VCPM 的，VCPM 没有该 SG 的上下文）。未验证。
- 下一步候选（要问用户）：在 `q6voice_build_graph`/GRAPH_OPEN 里追加 `miid 4 / 0x08001162`（TX 两条、RX 的 0xb0000040 一条）与 `miid 1 / 0x08001061` 控制链路，数据由 `fuxi-voice-graph-gen.py` 从 ACDB JSON 生成；可顺带补 SG/容器的额外属性。RX 图是否换成听筒别名（含 0xb00001d9/0xb0000045）另议。

### 7n. 额外属性与图内连线：离线取数和 RX 侧对比方案（2026-11-02，只读，未上机）
数据来源：`work/claude-logs/android-voice-shmdump2-20261102/` 的 TX 块 `pkt0138-…-map1-7703003000.bin`（0x1000, 0xdd8）与 RX 块 `pkt0104-…-map0-7703003000.bin`（0x1000, 0xdf0），用 `fuxi-graphopen-parse.py dump/cmp` 解析。
- 【已实测，离线】TX（Android 块，与我们的 TX 的 SG/容器 id 相同）要补的额外属性：
  - SG 属性 `0x080010cc`，值 0xffffffff：`0xb000003f`、`0xb00000b1` 各一份；`0xb0000039`（scenario 为 0xffffffff）没有。
  - 容器属性（`0x080010cb` / `0x08001174` / `0x0800124d`）：`0xe000004d` = ffffffff/1/1；`0xe000011d` = ffffffff/1/1；`0xe00000eb` = ffffffff/1/2；`0xe0000045` = ffffffff/2/1。
  - 图内连线两条：`4167:15>4448:2`、`4456:1>47b8:2`。两端都在我们的 TX 模块表里，都跨子图。
- 【已实测，离线】这两条连线被丢掉的原因：`fuxi-voice-graph-gen.py` 按 ACDB 的 `src_in_graph`/`dst_in_graph` 分类，把它们归入「图外连线」（`q6voice-graphs.h` 注释）。其余 6 条 TX 外部连线的对端（4021、4072、4862、49b2、4a78、4a9b）确实不在我们的 TX 模块表里。
- 【已实测，离线】RX 侧没有可逐项对的基准：Android RX 是听筒图（SG 45/1d9/41/40，容器 15a/17b/240/4e），我们的是扬声器图（SG 02/43/42/41/40），只有 SG 0x41/0x40 和容器 `0xe000004e` 相同（`cmp` 输出）。我们 RX 的 4 条「不发」连线 `418e:25>467e:4`、`418e:27>41e2:4`、`418e:29>48e7:2`、`4561:3>4085:2` 的对端（467e、41e2、48e7、4085）都不在我们的 RX 模块表里，是真外部连线。所以 RX 没有「被误丢的图内连线」，候选 (b) 在 RX 上为空，只剩候选 (a)。
- 【已实测，离线】Android 两个块里额外属性的规律（RX 的 5 个容器记录、TX 的 4 个）：
  - `0x080010cb` 全部是 0xffffffff。
  - `0x0800124d` 在 graph_pos=3 的容器上为 2，其余为 1（TX：`eb`=2；RX：`15a`、`240`=2）。
  - `0x08001174` 几乎都是 1，唯一例外是 TX 的 `0xe0000045`（graph_pos=4，所在 SG 的 scenario 为 0xffffffff）= 2；RX 的 `0xe000017b`（graph_pos=4）是 1。
  - `0x080010cc` 只出现在 scenario=3 的 SG 上，scenario=0xffffffff 的 SG 没有。
- 【推测】RX 方案：按上述规律给我们的 RX 补属性，不动连线。
  - SG：`0xb0000042/41/40`（scenario 3）加 `0x080010cc` = ffffffff；`0xb0000002/43`（scenario 0xffffffff）不加。
  - 容器：6 条记录（`e0000002`×2、`e0000101`、`e0000050`、`e000004e`×2）全部 `10cb` = ffffffff、`1174` = 1；`124d` 按 graph_pos：pos 4 的 `e0000002`×2 = 1，pos 3 的 `e0000101`、`e0000050` = 2，pos 1 的 `e000004e`×2 = 1。
  - `0x08001174` 取值规则只有 TX 一个反例，RX 取 1 是否对【未验证】。
- 位掩码模块参数设想（`voice_extra`，只对模式 0 生效）：bit0 = TX 的 SG/容器额外属性，bit1 = TX 补 2 条图内连线，bit2 = RX 的 SG/容器额外属性。bit0/bit1 先分开跑，都被拒再跑 bit0+bit1+bit2（TX、RX 各有一份就够，见 §7m）。
- 实现注意：`audioreach.c` 的 SG/容器记录是固定属性个数（`APM_SUB_GRAPH_CFG_NPROP` = 3，容器 4 个），要么让构造函数支持每条记录带可选的额外属性，要么在 `q6voice_build_graph()` 里自己拼 SG/容器记录。额外属性放进 SG/容器记录本身才和 Android 块一致，追加到 `extra_params` 不等价【推测】。这一点上机前要定。
