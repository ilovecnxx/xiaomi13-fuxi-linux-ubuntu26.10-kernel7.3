## 1. 消息 ID 和 TLV

**最容易踩的坑：各服务的"第二张卡"取值不一样。** NAS/VOICE/WMS/IMSA/IMSS 从 0 开始（0 主、1 副）；WDS/DMS/DSD 从 1 开始（0 默认、1 主、2 副）。libqmi 的 `QmiSubscriptionType` 也从 1 开始，用于 WDS/QOS。【有出处】依据：`network_access_service_v01.h:85-87`、`imsa.h:248-250`、`ip_multimedia_subsystem_settings_v01.h` 的枚举（WOS `ip_multimedia_subsystem_ims_common_v01.h:110-117`）、`device_management_service_v01.h:263-264`、WOS `wireless_data_service_v01.h:159-163`、WOS `data_system_determination_v01.h:112-114`、libqmi `src/libqmi-glib/qmi-enums.h:247-253`。

**查副卡注册状态：** 用一个已经发过 NAS 0x0045=1 的 NAS client，再调 libqmi 现成的 Get Serving System（0x0024）、Get System Info（0x004D）、Get Signal Info（0x004F）。IDL 写的是 "Binds the current control point"，所以绑定只对这一个 client 生效，【有出处】见上面的 bind 注释。之后同一个 client 上的类型化调用都作用于副卡，这一点是【推测】，但 qcril 就是这么用的（见 §4）。

## 2. 上游 libqmi / ModemManager

- 【有出处】libqmi **!476**（open，EpicLPer，2026-09-24，最后更新 10-11）：新增 NAS Set/Get Dual Standby Pref（0x4B/0x5C）和指示 0x47，标为 since 1.40。作者说在 Lumia 950XL（MSM8994）上，基带的 active_subs_mask=0 导致完全不驻网，发一次设置就好了；这个掩码不写入 EFS，基带每次重启后都要重发。https://gitlab.freedesktop.org/mobile-broadband/libqmi/-/merge_requests/476
- 【有出处】已合并的相关 MR：libqmi !478 UIM Subscription OK（0x0040，2026-09-29）、!459 IMSA Get Bind（1.40）、!434 WDS/QOS Bind Subscription（1.38）、!379 IMS Bind、!378 UIM 双卡 PIN。
- 【有出处】2026-11-01 在 freedesktop GitLab 按 subscription / dual sim / DSDS / standby / multi-sim 搜索 libqmi 和 MM 的 MR，**没有** NAS/VOICE/WMS/DMS bind subscription 的 MR。
- 【有出处】MM 的态度：**一个 modem 对象，带多个 SimSlots，只有一个 primary slot**。!330（2020 年合并）加了多 SIM API，但 QMI 只实现了单待；作者说"multi-standby…shouldn't be hard"，之后一直没人做。https://gitlab.freedesktop.org/mobile-broadband/ModemManager/-/merge_requests/330
- 【有出处】MM issue #761 "Dual SIM support for QMI modems"（2023 年起 open，无人认领）：报告者说 Secondary GW 存在时 MM 会断言失败；我们这台没出现这个问题。#649：把 UIM 选卡并进 MM。!1504（open）：MM 自己选卡并发 Subscription OK，**只处理主卡**。
- 【有出处】MM 源码：`src/mm-modem-helpers-qmi.c:2936` 有 "We don't really support Dual Sim Dual Standby yet"；`src/mm-shared-qmi.c:3713` 的 refresh 只处理 slot1/primary-GW；MM 源码里没有任何 `bind_subscription` 调用，所以 MM 的 WDS/NAS client 都没绑定，跟随默认（主卡/DDS）。
- 【推测】短期内上游不会出现"每个订阅一个 modem 对象"。副卡只能由我们自己的用户态工具单独管理，不经过 MM。

## 3. 81voltd

- 【有出处】上游：https://gitlab.postmarketos.org/modem/81voltd （会重定向到 gitlab.nura.eco），作者 Richard Acayan，GPL-2.0+，最新 tag v1.2.0。
- 【有出处】**不支持第二个订阅，也没有任何配置项。** `main.c:11-40` 不接受参数；`qvd-server.c:126` 只发布一个 `qrtr_new_server(fd, 770, 1, 0)`（服务 770，版本 1，实例 0）；`qvd-modem.c:265-289` 只找端口名为 `qrtr0` 的那一个 MM modem。
- 【有出处】请求里的 subscription 只用来回填，**不影响建哪路 bearer**。`process_start_connection`（`qvd-server.c` 约 283-330 行）把 `req.subscription` 存进 connect_data，再原样写回响应和指示。bearer 一律用 `mm_modem_create_bearer` 在 MM 那个 modem 上创建（`qvd-modem.c:395-450`），走的是 MM 的 WDS，也就是主卡/DDS。
- 【有出处】bearer 去重的键只有 (IP 类型, APN)（`qvd-modem.c:291-304, 418`）。如果副卡也请求 `ims`/IPv6，会**直接复用主卡那路 bearer**，两张卡的连接会串在一起。
- 【有出处】TLV 含义两边对不上。81voltd 把请求的 0x13 叫 subscription（README "Thanks to Dylan's research"，`imsd.qmi:34-37`）。libqmi `qmi-service-imsdcm.json` 的说法是：0x11 = PDP Subscription Id，0x12 = PDP Slot Id，0x13 = Instance Id（`QmiImsDcmInstanceId`：1 Global、2 ID1、3 ID2）。README 的主卡示例是 0x11=0、0x12=1、0x13=1。
- 【推测】副卡请求 IMS PDN 时，大概是 0x11=1、0x12=2、0x13=? 。验证方法：给 81voltd 加 `G_MESSAGES_DEBUG=all`（README 有写），看日志里 "Req: Start connection, conn X, sub Y"。
- 【推测】副卡 IMS PDN 的正确建法：另开一个 WDS client 并 Bind Subscription=2（libqmi 1.38 已有），用请求里的 profile 号做 Start Network，再按需 Bind Mux Data Port 到一个 MM 没在用的 mux id。WDS profile 是按订阅分开存的，直接把这个 profile 号交给 MM 那路 WDS 会查成主卡的 profile。IMS 协议栈跑在基带里，AP 侧可能不需要真正接通数据通路，这一点没有资料证实。81voltd 要支持副卡，需要按 subscription 分流的补丁；也可以由我们的工具接管副卡的 770 请求，但同一节点上不能有两个 770/实例0 的服务端，所以只能改 81voltd 本身。

## 4. 其他项目怎么做

- 【有出处】postmarketOS：`soc-qcom` 默认装 `msm-modem-uim-selection` 和 `81voltd`（pmaports `device/community/soc-qcom/APKBUILD:88-90`，`soc-qcom-modem-openrc.post-install:5-6`）。选卡脚本只把**第一个有卡槽位**的 USIM 设成 primary-gw（https://gitlab.postmarketos.org/postmarketOS/msm-modem 的 `msm-modem-uim-selection` 第 83-97 行），没有任何 DSDS 处理。sdm845/sm8x50 设备也是一样。
- 【有出处】oFono qmimodem：没有任何 bind subscription，只有 WDS Bind Mux Data Port（`drivers/qmimodem/wds.h:146-151`），是单订阅设计。
- 【有出处】Droidian / Ubuntu Touch / Sailfish 走 Android 厂商 RIL（qcril），通过 binder 加 ofono-binder-plugin，配置里按 `[slot1]`/`[slot2]` 分。DSDS 由 qcril 完成：**每张卡一个 RIL 实例**，每个实例初始化后对自己的 NAS/VOICE/PBM/WMS/DMS(/LTE) client 依次发 Bind Subscription。代码在 CAF `qcril/qcril_qmi/qcril_qmi_client.c:2071-2236`，在 914 行调用。IMSA 按 stackId 0→PRIMARY、1→SECONDARY 绑定（`qcril-nr/modules/qmi/src/ImsaModemEndPointModule.cpp:40-75`），NAS 也一样（`NasModemEndPointModule.cpp:54-65`）。**这就是下面步骤的参考顺序。**
- 【有出处】ofono-binder-plugin 的 `binder.conf:34-40` 提到，老平台两个卡槽共用一个 3G/LTE 模块，同一时刻只有一张卡能用 LTE。【推测】SM8550 支持 DSDS 甚至 DSDA，副卡在 LTE/NR 上做 IMS 应该可以，但我们的基带配置未知。

## 5. 用 libqmi GI 发自定义 QMI 消息（已在 PC 上离线验证，只组包和解析，没有发给设备）

```python
c = client(Qmi.Service.NAS)                       # 先 allocate_client，非 CTL 服务必须有 CID
m = Qmi.message_new(Qmi.Service.NAS, c.get_cid(), c.get_next_transaction_id(), 0x0045)
off = Qmi.message_tlv_write_init(m, 0x01); Qmi.message_tlv_write_guint8(m, 1); Qmi.message_tlv_write_complete(m, off)
# 4 字节值：Qmi.message_tlv_write_guint32(m, Qmi.Endian.LITTLE, 2)；8 字节掩码：循环写 8 次 guint8
ctx = Qmi.MessageContext.new()
print(Qmi.message_get_printable_full(m, ctx, ""))  # 调试用；ctx 不能传 None
_, res = wait(dev.command_full, m, ctx, 10, None)  # 沿用 fuxi-qmi-ims.py 的 wait()
resp = dev.command_full_finish(res)
off, ln = Qmi.message_tlv_read_init(resp, 0x02)    # 结果 TLV
_, o, status = Qmi.message_tlv_read_guint16(resp, off, 0, Qmi.Endian.LITTLE)
_, o, err = Qmi.message_tlv_read_guint16(resp, off, o, Qmi.Endian.LITTLE)  # Qmi.ProtocolError(err)
# 读任意 TLV：read_init(resp, t) 返回 (off, len)，再循环 read_guint8；TLV 不存在时抛 GLib.Error
```
- 【有出处】libqmi 用 (service, cid) 把消息路由到该 client 自己的 QRTR socket（`qmi-endpoint-qrtr.c:195, 537-556`）。CID 为 0 的消息会被拒绝（`qmi-device.c` 约 3025 行 "Cannot send message … without a CID"）。所以原始消息和同一 client 的类型化调用共享同一个绑定。
- 【有出处】已验证的坑：`Qmi.message_add_raw_tlv` 在 GIR 里把 raw 参数标成单个 guint8，Python 里没法用，**别用**；`Qmi.message_get_raw` 返回的是指针，也没法用。原始指示可以从 `Qmi.Device` 的 "indication" 信号拿到（`qmi-device.c:1806`），用来解析 NAS 0x47/0x48。
- 【有出处】绑定在进程退出后就失效，qmicli 在 QRTR 上不能跨进程复用 CID，这一点交接文档里已经实测过。所以副卡工具必须是一个**常驻进程**，一直持有自己绑好的 client。

## 6. 建议的最小步骤（副卡工具，与 MM 并存，不碰 UIM 选卡）

1. **只读：** 读 UIM card status（确认 Secondary GW = slot2 app2 是 ready）；读 NAS 0x005C（standby_pref、掩码）；在**未绑定**的 NAS client 上读 0x007C 和 0x0049。
2. 如果掩码里没有 bit1，发 NAS 0x004B：`10 01 00 05` 加上 `14 08 00 03 00 00 00 00 00 00 00`（只带这两个 TLV）。回退方法是把掩码设回 0x01。【推测】这会给主卡带来 tune-away，影响很小。基带重启后要重发（MR !476 的说法）。
3. 新开 NAS client B，发 0x0045=1，然后在 B 上：0x007C（is_active 应为 1）、Get Serving System / Get System Info / Get Signal Info、Indication Register（打开 serving system、sys info、0x14、0x15）。副卡注册上之后再做下一步。
4. 新开 IMSS client，发 Bind 0x0098=1，读 IMS 开关；用原始 PDC 0x0022 带 TLV 0x11=1，确认副卡选中了电信的 MBN。【推测】电信 VoLTE 需要电信 MBN，并且 IMS 要在副卡上启用。
5. 新开 IMSA client，Bind=1，查注册状态（0x0020）和 0x0036（libqmi 1.38 没有，需要发原始消息）。同时开着 81voltd 的调试日志，看基带有没有为副卡发 770 Start Connection。没有请求，说明副卡 IMS 还没被触发（MBN 不对，或者副卡没在 LTE/NR 上）。有请求，就要给 81voltd 打按 subscription 分流的补丁（§3）。
6. 短信/语音：VOICE client 发原始 0x0044=1，WMS client 发原始 0x004C=1，之后都用 libqmi 现成的类型化调用（来电指示、拨号、Raw Send、Transport NW Reg 等）。按需给 DMS client 发 0x0054（4 字节值 2）查 IMEI2。
7. 保持 DDS 在主卡，不发 DSD 0x004E。MM 和 keeper 不用改。
