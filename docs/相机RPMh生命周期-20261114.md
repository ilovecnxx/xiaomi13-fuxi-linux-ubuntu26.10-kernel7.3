# RPMh 批量请求超时生命周期候选

本轮继续针对相机重启时已复现的 MM0 超时处理内核错误路径。
手机仍运行 deb9，默认 deb9、回退 deb8，启动计数为零；没有安装本候选或重跑
已知会阻塞的相机重启矩阵。候选位于独立 `rpmh-lifetime` 配方，不属于标准内核。

## 修复范围

`rpmh_write_batch()` 原先在等待超时后立即释放整个批量请求，包括 RSC 仍引用的
命令和 completion。若硬件稍后完成，IRQ 路径会继续访问已释放内存。
原源码已有注释承认这个风险；本机 MM0 超时说明该错误路径确实可达，但没有证据
证明此前整机阻塞已经发生了迟到 IRQ 或实际内存破坏。

候选为 active batch 增加引用计数：调用者持有一个引用，每次提交前增加一个
硬件引用；提交失败立即退还该引用，成功提交由 `rpmh_tx_done()` 在完成通知后
退还。调用者正常返回或超时只释放自己的引用。命令和 completion 一同保留到
最后一个使用者结束，避免只延长 completion 而遗漏命令内存。

同时在任何发送/缓存前验证全部请求长度，拒绝超出 `MAX_RPMH_PAYLOAD` 的批次；
原来忽略 `__fill_rpmh_msg()` 返回值可能继续发送未初始化的请求。分配大小采用
溢出检查辅助函数。sleep/wake 缓存仍由原来的 invalidate 路径释放。
保留超时错误和诊断输出，去掉超时路径中重复的 `WARN_ON(1)`。

## 验证

- ARM64 GCC 15.3.0，原相机配置 SHA256
  `9d8c8497b051974e912e27eb46bddd54c22e59f3ad7c2429efcaa6dc6a5edb95`；
  `W=1 drivers/soc/qcom/rpmh.o drivers/soc/qcom/rpmh-rsc.o` 编译通过。
- x86_64 QEMU 内核启用 KASAN，直接调用实际 `rpmh_write_batch()` 和
  `rpmh_tx_done()`；只替换发送/寄存器快照入口，不访问真实 RPMh 硬件。
- 7 项测试覆盖反序完成、首条提交失败、前条完成后后条失败、多个请求超时后迟到
  回调、部分提交失败后前条超时及迟到回调、非法长度/空批次、sleep/wake 缓存。
  两个超时测试保留实际 10 秒等待，不缩短生产代码超时。
- 7 项全部通过，未报告 KASAN 错误；超时返回后检查命令数据、completion 和引用
  计数，再模拟迟到 IRQ，验证仍有未完成请求时内存有效。
- `checkpatch.pl --no-tree --no-signoff` 为 0 错误，保留 1 条新增文件的通用
  MAINTAINERS 提醒；现有 Qualcomm 条目的 `drivers/soc/qcom/` 已覆盖测试文件。
- 补丁从固定父树独立应用，结果树为
  `62c582439fc1dd6900351df1b789b78a4ebe0f94`，与配方一致；严格主机回归通过
  366 项脚本测试和 62 项 SuperTerm 测试。deb9 无线/传感器健康检查失败项为 0，
  原有轴向/单位警告仍保留，不等于相机或全部传感器验收。

日志仅留在本地 `work/camera-rpmh-lifetime-20261114/`，原始设备资源快照不发布。

## 仍未解决

这不是 MM0 硬件超时修复，也不能据此重新启流或宣称四摄可用。

1. `rpmh_rsc_send_data()` 等待空闲/无冲突 TCS 仍没有时限；本候选不改变硬件状态，
   不清除占用 TCS、不伪造响应、不回滚未完成的投票。
2. 硬件永不完成时，其请求内存必须继续保留；没有取消/复位协议便不能释放。
3. 单条同步 `rpmh_write()` / `rpmh_read()` 仍使用栈请求，需要单独解决迟到回调；
   异步提交失败的释放路径也需要一起审查，不能把批量修复扩称为全部 RPMh 完成。
4. `qcom_icc_set()` 的 voter 错误传递及消费者回滚仍待处理，必须与请求生命周期、
   有界等待和硬件恢复设计配合，不能单独返回错误后任意掉电。
5. cam6 的 HF 门控假设已被同进程第二次启流反例否定为充分修复。VFE 的 CAMNOC
   时钟、共享显示消费者和电源域时序仍需采集失败当时的证据。

本轮只读 deb9 空闲快照显示相机 HF/CAMNOC 时钟引用为零、TITAN_TOP 关闭，显示
MDP 时钟仍打开。快照不来自 cam6 故障现场，不能用于证明失败时具体哪个时钟关闭。
vendor kalama 的 MM0 有 `keepalive_early`，不等于需要永久 keepalive；不能据此
以常驻带宽或永久 runtime PM 引用作为修复。
