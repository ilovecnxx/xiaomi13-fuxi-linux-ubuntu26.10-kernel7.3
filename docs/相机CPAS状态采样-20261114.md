# CPAS 停流时序调查与状态采样

本实验调查超广角重复启流的 MM0 阻塞。当前新增的是 CPAS 版本与 Q-channel
只读采样，尚未实现握手，也没有证明缺失握手就是故障原因。它不代表四摄、
拍照录像或原厂徕卡算法已经完成。

## 新的源码依据

公开参考固定为 MiCode `vendor_qcom_opensource_camera-kernel` 的 fuxi-t-oss
提交 `6c6099a85cb3154fc8a744c17b6b9f5fd361dea8`：

- [cam_cpas_hw.c](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cam_cpas_hw.c)：
  start 先建立 AHB/AXI 投票，再启用资源并执行 Q-channel 上电检查；stop
  在资源关闭前执行 Q-channel 空闲握手，之后才撤销投票。因此“所有相机内部
  时钟都必须先于投票打开”并不能直接由原厂实现推出。
- [cam_cpastop_hw.c](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cpas_top/cam_cpastop_hw.c)：
  上电等待 QACCEPTN；停机向 Q-channel control 写 0，等待 QACCEPTN/QDENY
  清零。部分错误仍允许调用者继续，不能照搬其错误处理作为可靠恢复设计。
- [cpastop_v780_100.h](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cpas_top/cpastop_v780_100.h)：
  Titan 780 的握手需要临时启用 ICP 时钟。CSID 驱动文件名中的 680 不能用于
  判断整个 CPAS/Titan 的版本。

本机已保存的 Android 设备树确认 CPAS top 区域为 `0x0ac13000/0x1000`，

厂商完整寄存器配置表或专有算法二进制。

## 隔离实现

配方在 `kernel/experiments/camera/cpas-diag/`，父配方为 RPMh 生命周期候选，
结果树 `e4439f14fa6004e92ca40429e900f7e4c25d7966`。三个补丁分别增加可选
CPAS top 绑定、驱动采样和 SM8550 资源描述，标准内核/APT 清单不变。

采样只在 VFE 时钟已经成功开启后执行，位置为上电复位成功、复位错误清理、
最终 VFE halt 前及关时钟前。缺少可选资源时直接返回。probe 阶段只映射，
不读寄存器；runtime resume 失败时也不读。

每条记录包含 camera/CPAS version、control、前后两次 status。两个 status
读数不构成原子快照；日志和 MMIO 读取会影响时序。单个 VFE 的最后一个引用
不等同于所有 CPAS 客户端已停止，不能据此直接在 `vfe_put()` 写停机请求。

## 主机验证

- ARM64 `W=1 -j4 drivers/media/platform/qcom/camss/` 编译通过，无 C 编译告警。
- `qcom/sm8550-xiaomi-fuxi-ov13b10.dtb` 编译通过，DTC 报告既有 DSI 节点
  `avoid_unnecessary_addr_size` 警告；没有宣称整棵设备树零告警。
- 固定容器中的 `dt_binding_check DT_SCHEMA_FILES=media/qcom,sm8550-camss.yaml`
  通过，包含格式、schema 和旧 19 区域示例。
- 对新增 20 区域的真实 OV13B10 DTB 运行 CAMSS 定向 `dt-validate`，无输出。
  这不是整个板级设备树的全量 schema 验收。
- 独立 Git index 从父提交重新应用三补丁，结果树一致。
- `checkpatch.pl --no-tree --no-signoff` 通过；未伪造维护者 DCO 签字，普通
  checkpatch 仍报告缺少 Signed-off-by，不能作为已满足上游提交门槛。

## 后续门槛

先根据真实版本和状态核实握手适用条件，再设计全局 CPAS 用户计数、ICP 时钟、
停机次序与超时回滚。RPMh 超时请求仍可能在硬件内执行，不能仅因软件等待
结束就断电或重提旧投票。即使单次采集通过，也仍需解决 MM0、同进程重启、
画质和桌面相机流程；主摄 C-PHY、另外两摄、AF/OIS 与原厂后处理依赖独立存在。
