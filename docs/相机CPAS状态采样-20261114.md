# CPAS 停流时序调查与状态采样

本实验调查超广角重复启流的 MM0 阻塞。当前新增的是 CPAS 版本与 Q-channel
只读采样，尚未实现握手，也没有证明缺失握手就是故障原因。它不代表四摄、
拍照录像或原厂徕卡算法已经完成。

## 新的源码依据

公开参考固定为 MiCode `vendor_qcom_opensource_camera-kernel` 的 fuxi-t-oss
提交 `6c6099a85cb3154fc8a744c17b6b9f5fd361dea8`：

- [cam_cpas_hw.c](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cam_cpas_hw.c)：
  start 先建立 AHB/AXI 投票，再启用资源并执行 Q-channel 上电检查；stop
  在资源关闭前执行 Q-channel 空闲握手，之后才撤销投票。因此“所有相机内部
  时钟都必须先于投票打开”并不能直接由原厂实现推出。
- [cam_cpastop_hw.c](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cpas_top/cam_cpastop_hw.c)：
  上电等待 QACCEPTN；停机向 Q-channel control 写 0，等待 QACCEPTN/QDENY
  清零。部分错误仍允许调用者继续，不能照搬其错误处理作为可靠恢复设计。
- [cpastop_v780_100.h](https://github.com/MiCode/vendor_qcom_opensource_camera-kernel/blob/6c6099a85cb3154fc8a744c17b6b9f5fd361dea8/drivers/cam_cpas/cpas_top/cpastop_v780_100.h)：
  Titan 780 的握手需要临时启用 ICP 时钟。CSID 驱动文件名中的 680 不能用于
  判断整个 CPAS/Titan 的版本。

三份下载文件的 SHA256 依次为：


本机已保存的 Android 设备树确认 CPAS top 区域为 `0x0ac13000/0x1000`，
并列出可选 ICP 时钟。公开仓库只保存引用和最小接口信息，不加入原始设备树、
厂商完整寄存器配置表或专有算法二进制。

## 隔离实现

配方在 `kernel/experiments/camera/cpas-diag/`，父配方为 RPMh 生命周期候选，
结果树 `e4439f14fa6004e92ca40429e900f7e4c25d7966`。三个补丁分别增加可选
CPAS top 绑定、驱动采样和 SM8550 资源描述，标准内核/APT 清单不变。

采样只在 VFE 时钟已经成功开启后执行，位置为上电复位成功、复位错误清理、
最终 VFE halt 前及关时钟前。缺少可选资源时直接返回。probe 阶段只映射，
不读寄存器；runtime resume 失败时也不读。

每条记录包含 camera/CPAS version、control、前后两次 status。两个 status
读数不构成原子快照；日志和 MMIO 读取会影响时序。单个 VFE 的最后一个引用
不等同于所有 CPAS 客户端已停止，不能据此直接在 `vfe_put()` 写停机请求。

## 续接实机采样（2026-11-15，Asia/Tokyo）

主机与手机日志使用 UTC+8，文件名仍为 `20261114`；本节日期按会话时区 UTC+9。
网络恢复后重新核对手机运行/默认 deb9、回退 deb8，启动计数全零，设备支持包
与仓库一致。deb9/deb8 的 Image、DTB、initrd 和 cmdline 校验全部通过，根 UUID
匹配，根文件系统可写，没有失败服务或 D 状态进程。

再次验证原 `cam7cpas` 产物及传到手机的 deb 哈希，使用临时配置选择 OV13B10
DTB 并安装。候选与两个回退条目校验通过，安装后删除临时配置。正常 recovery
重启进入 `7.4.0-rc1-fuxi-cam7cpas`，自动启动确认完成、计数归零；在打开相机前
已将下次默认设回 deb9、回退设为 deb8。

仅以普通 `fuxi` 用户执行一次短 RAW 采集：

```bash
runuser -u fuxi -- env LIBCAMERA_SOFTISP_MODE=cpu \
    timeout -k 3s 25s cam -c 1 -s role=raw,width=2104,height=1560 -C5
```

实测格式为 `2104x1560-SGRBG10_CSI2P/RAW`，序号 0 到 4 连续，五帧的
`bytesused` 均为 4,118,400，进程退出码为 0。未保存图像，未进行画质验收；
RAW 路径也不验证软件 ISP。本轮没有第二次启流，没有注入 RPMh 超时。
libcamera 仍报告传感器 crop/selection、静态属性、延时及标定文件缺失，不能把
正常退出当作这些接口已完善。

三个采样点均来自 VFE 0：

| 阶段 | camera version | CPAS version | control | status 前 → 后 |
|---|---|---|---|---|
| `reset-done` | `00070800` | `10000000` | `00000001` | `00000000` → `00000000` |
| `before-halt` | `00070800` | `10000000` | `00000001` | `00000000` → `00000000` |
| `before-clock-off` | `00070800` | `10000000` | `00000001` | `00000000` → `00000000` |

按原厂 `cam_cpastop_get_hw_info()` 的位域解码，camera 为 7.8.0、CPAS 为
1.0.0，对应 Titan 780 V100。该版本确实选用 `enable_icp_clk_for_qchannel`
处理路径。原厂上电要求 status bit 0 (`QACCEPTN`) 为 1；停机先写 control=0，
再等待 status bits 0/1 (`QACCEPTN`/`QDENY`) 均清零。
本轮 control 一直为 1，没有执行该停机请求，不能将 status=0 宣称为握手成功。
现有采样也未临时开启 ICP 时钟，没有握手期间的 ICP 时钟证据；零读数尚不能
区分有效状态与缺少时钟推动的状态，亦不能证明它导致了 MM0 超时。

采集脚本退出时 HF enable 已为零，CPAS AHB/CAMNOC enable 暂仍为 1；后续独立
只读快照中三者均为零，CAMSS suspended，TITAN_TOP off，ICP enable 为零。
这说明不能只凭进程刚退出时的时钟行判定泄漏；也不证明关电前完成了握手。
本次启动日志没有 RPMh 超时、AMC 发送失败、hung task 或存储错误。

随后正常重启回 deb9，默认 deb9、回退 deb8，`pending=0 tries=0 once=0`；
两个启动条目再次校验通过，根文件系统可写，没有失败服务或 D 状态进程。
`scripts/fuxi-health.sh --require-wifi --require-sensors` 失败项为 0，Phosh
本次启动无需重试。既有传感器轴向/单位警告仍保留。候选包保留安装但不是默认，
没有手动清除 BCB，也没有写入 Android/固件分区或更换系统相机库。

## 后续门槛

本轮已核实 Titan 780 / CPAS 1.0.0；下一步需在电源域和 AHB 可用期间，按该
版本的原厂流程核实临时开启 ICP 后的状态及其有限等待条件，并记录失败清理。
这需要新的隔离候选和单次实机验证，不能在已 runtime suspend 的设备上直接读寄存器。
再设计全局 CPAS 用户计数、ICP 时钟、
停机次序与超时回滚。RPMh 超时请求仍可能在硬件内执行，不能仅因软件等待
结束就断电或重提旧投票。即使单次采集通过，也仍需解决 MM0、同进程重启、
画质和桌面相机流程；主摄 C-PHY、另外两摄、AF/OIS 与原厂后处理依赖独立存在。

当前 `vfe_put()` 在 `pm_runtime_put_sync()` 之前已关闭该 VFE 时钟，而
`camss_runtime_suspend()` 才撤销带宽并关闭共享 HF 时钟。因此不能直接把
需要 CPAS AHB/ICP 的握手插到现有 runtime suspend 尾部，也不能把某个 VFE 的
最后引用当作全局无人使用。后续必须覆盖共享资源的持有顺序、其他 VFE/CSID/PHY
用户和复位失败路径；遇到未确认的硬件请求时必须明确恢复方式。
