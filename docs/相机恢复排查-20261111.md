## 新确认的证据

输入是 `../01-project-tree/work/camera-20261108/cam4-rpmh-failure-trace.log` 与同目录的 `cam4-rpmh-failure-dmesg.log`，不是新实机结果。

| --- | --- |

| 1198.557445 | CAMSS 仍被标为 RPM_ACTIVE |
| 1198.557451 | rpm_resume 返回 0 |

同一 trace 中此前八次完整恢复间隔为 0.288–1.727 ms，最后一次为 **10.237084 秒**。这是 runtime-PM 状态事件间隔，不能直接当作单次硬件请求延时。

源码解释了为何超时后仍出现成功状态：`drivers/interconnect/qcom/icc-rpmh.c` 中 `qcom_icc_set()` 调用 `qcom_icc_bcm_voter_commit()` 后无条件返回 0；后者在 AMC 提交失败时实际返回错误。因而 CAMSS 的 `icc_set_bw()` 错误分支不能看到该提交失败。这是错误传播缺口，尚不能据此确定最初的硬件超时原因。

不能只改一行返回值就声称修好：`drivers/interconnect/core.c` 的 `icc_set_bw()` 在失败时会持有全局 `icc_bw_lock` 再次调用 `apply_constraints()` 回滚；`rpmh-rsc.c` 的发送路径存在等待 TCS 可用的等待点。若控制器已经卡住，回滚仍可能阻塞共享互连。需要在独立实验树验证错误传播、请求生命周期及失败收尾，不直接改标准配方或刷回旧 cam4。

## 关键跟踪缺口

最终故障 trace 内 **rpmh_send_msg 和 rpmh_tx_done 均为 0 条**，因此不能从该文件定位哪个 TCS 或资源最先未完成。

恢复出的 `test-cam4-stall-stack.sh` 第 9 行明确将同一个 `fuxi-camera` instance 的 `events/rpmh/enable` 写为 0。最初的 `setup-cam4-trace.sh` 虽然启用了 RPMh，但后续测试改变了开关；最终 trace 的缺失与此一致。早期 `cam4-trace-mixed.log` 中确实存在 RPMh send/done 事件。不能将最终 ring 的 overrun=0 理解为关键事件已完整采集，也不能把每个命令的 send 与批次级 tx_done 数量直接一一配对。

新工具可重复提取事件数量、标记、CAMSS 电源状态和恢复间隔：

```bash
python3 scripts/fuxi-camera-trace-audit.py \
  ../01-project-tree/work/camera-20261108/cam4-rpmh-failure-trace.log
```

工具只读本地文件，输出 JSON；缺少 RPMh 事件时明确报告证据不足，不推断无故障。原始日志中的拼接异常、trace_pipe 消费及采集开关变化仍需人工核对。
