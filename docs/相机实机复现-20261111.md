# 相机实机复现（2026-11-11）

## 结论

复现 cam4 的共享互连阻塞，首次保存了故障时间窗口内可配对的 RPMh 请求/完成事件。未修复内核。半尺寸与单次全尺寸采集通过不能推翻故障结论。当前需要物理恢复；正常重启请求未完成，不能记为已经回退。

## 实机基线与改动

- 实际初始内核为 deb9，默认 deb9、回退 deb8，pending=0 tries=0 once=0。这与 11 月 8 日的 std2 记录不同。
- 初始根分区 `/dev/sda33` 为 rw；dpkg 审计无输出，采样无持续 D 状态线程，未见 RPMh 批次超时或 EXT4/I/O 错误。
- deb9 有 OV13B10/CAMSS，但无系统 DMA heap，libcamera 不能启用软件 ISP。
- 手机已有 cam4。逐项校验 cam4、deb9、deb8 的启动目录 SHA256SUMS 全通过。
- 仅切换 Linux 启动条目并正常 recovery 重启到 cam4，没有刷写 recovery、Android 或固件分区。cam4 启动确认通过后，立即预置下一次默认 deb9、回退 deb8；故障后仍读取到这两个值。
- 发现手机缺失仓库现有的 `81-fuxi-camera.rules`，将其部署至 `/etc/udev/rules.d/81-fuxi-camera.rules`，udev 校验通过。系统 heap 从 root:root 0600 变为 root:video 0660，普通 fuxi 用户实际 RGB 采集通过。规则 SHA256 为 `1a7e74c175ef6987cc9b59f4f03a2d2eaaa5f3a88a0d6312429944b0715656cc`。没有安装整套设备包或覆盖已有同名文件。
- 未设置全局 CPU ISP。CPU 模式只用进程环境变量。为了检查桌面取景，曾通过 ScreenSaver D-Bus 请求点亮屏幕，没有重启桌面。

## 完整故障链

`trace-matrix.log` 的对照窗口自 1043.347490 秒开始，离线工具配对到 9,130 个完成的 active 批次、1 个未见完成的批次；该窗口没有配对异常。整个文件较早部分存在配对异常，不能宣称整个会话无损；故障窗口还需结合 dmesg 与线程栈判断。

1. 1053.588374：半尺寸退出后立即标记 `cpu-matrix-1-full`。
2. 1053.697784：CAMSS 的配置 AHB 路径两条命令提交到 TCS 0，1053.697803 收到完成确认；配置路径正常返回。
3. 1053.698437：数据路径 `qnm_camnoc_hf -> ebi` 的六条命令提交到 **apps_rsc TCS 0**，后续未观察到该批次完成确认。
4. 等待期间 **TCS 1** 的其他电源请求仍有完成确认，不能将其描述为整个 RPMh 控制器或所有 IRQ 都失效。
5. 1063.869558：dmesg 报告六命令批次超时，资源和数值与旧 cam4 故障一致。
6. 1063.901147：该 CAMSS 数据路径的 `icc_set_bw_end` 仍返回 0；随后 RPM_ACTIVE，恢复间隔 **10.203457 秒**。与 `qcom_icc_set()` 忽略提交错误的源码行为一致。
7. `sugov:0` 阻塞在 `rpmh_rsc_send_data`；其他调频、UFS runtime resume 和相机 streamoff 阻塞在 `icc_set_bw`；jbd2 等待 `bio_queue_enter`。相机收到了 120 帧并不代表这轮成功或系统健康。
