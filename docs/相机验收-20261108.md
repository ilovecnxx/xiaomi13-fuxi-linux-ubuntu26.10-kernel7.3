# 相机实机记录（2026-11-08）

## 结论与限制

OV13B10 超广角已完成上电、芯片 ID、CAMSS、libcamera RAW 和软件 ISP RGB
采集，真实场景可见。相机功能仍未完成：高速模式有黑色短横线；曝光、色彩和
标定未验收；桌面取景未成功验证。cam4 对照中 GPU RGB 反复停帧；CPU RGB
2104×1560 连续 1200 帧通过，但随后全尺寸 CPU RGB 启流仍触发 RPMh 互连超时，
并阻塞 UFS 存储和 CPU 调频线程。cam3/cam4 均不能晋级为日常基线或发布版本。

标准配方 `kernel/manifest.json` 未改动。实验补丁、配置、源码树和复现命令见
[`kernel/experiments/camera/`](../kernel/experiments/camera/README.md)。
手机和主机上的原始日志、照片只留在忽略目录，不提交。

## 供电与传感器 ID

cam1 实验内核修复手动供电驱动缺少 TITAN_TOP runtime PM 的问题，四路 MCLK
可设置为 19.2 MHz，上电不再出现原来的 `status stuck at 'off'`。

| 模组 | 精确地址和寄存器 | 结果 |
|---|---|---|
| IMX800 主摄 | cci0 master1，0x10，0x0016 | 0x0800，3/3 匹配 |
| OV13B10 超广角 | cci0 master0，0x36，0x300a | 0x560d42，6/6 匹配 |
| OV32C 前摄 | cci1 master1，0x18，0x300a | 读到 0；期望值未确认，不能算成功 |
| S5K3K1 长焦 | cci1 master0，0x2d，0x0000 | 首次 0x30b1 匹配，后两次 CCI 超时 |

`scripts/fuxi-camera-identify.py` 使用上述精确地址，不扫描总线、不强制访问
已绑定设备；逐路上电、5 秒 I2C 超时、finally 断电，并加操作锁。测试后手动
节点均为 0。OV13B10 驱动接管后的 DT 禁用 cam2 手动节点，不能再用此工具
操作 cam2；应通过 media/V4L2/libcamera 测试。

## 采集结果

cam2 增加 OV13B10 OF 匹配、绑定和专用 DT，链路为：

```text
OV13B10 -> CSIPHY0 -> CSID0 -> VFE0 RDI0 -> /dev/video0
```

1. RAW：`2104x1560 SGRBG10_CSI2P`，5 帧，单帧 4,118,400 字节，约 59 fps，
   各帧哈希不同。传感器内置色条也采集成功，解包后颜色顺序正确，但可见局部黑色短线。
2. cam3 打开 `DMABUF_HEAPS` 和 `DMABUF_HEAPS_SYSTEM`，RGB 1280×720
   ABGR8888，root 10 帧、普通 fuxi 用户 30 帧采集成功，时间戳约 120 fps。
   这是短时采集结果，不代表持续性能或录像支持。画面偏暗并有短横线。
3. 普通用户 RGB 2104×1560，120 帧，约 29.7–29.9 fps；只覆盖同一 PPM 文件，
   未保存全部帧。最后一帧能清楚辨认桌面物体，较初始画面更亮；缩图目视未见先前
   明显的短横线，不代表已排除所有像素错误。
4. 第 3 项结束时控制值为 exposure=3188、analogue_gain=1478、digital_gain=2560。
   相比早先读数有变化，表明缺少 sensor helper 并不等于完全没有自动控制。
   尚无亮暗切换、收敛时间、曝光延迟或颜色准确性验收。

可用的短时诊断命令（仅在已恢复、可接受重启的实验环境使用）：

```bash
cam -l
timeout -k 5s 25s cam -c 1 -s role=raw,width=2104,height=1560 -C5 -F/tmp/fuxi-raw-#.bin
timeout -k 5s 25s cam -c 1 -s role=viewfinder,width=1280,height=720 -C30 -F/tmp/fuxi-last.ppm
```

超时不能终止阻塞在内核中的线程。不要并发启动多个采集程序，也不要自动循环
重试故障。PPM 可覆盖单帧；`.bin` 即使文件名不含 `#` 也会追加数据，不能用于
这种覆盖保存。长测省略 `-F`，避免大量 RGB 数据占满 `/tmp`。

## 失败记录与后续顺序

在完成 2104×1560 采集后，另一次请求 4208×3120 RGB 被 libcamera 调整为
4200×3120。未返回首帧，内核约 uptime=600 秒报告：

```text
rpmh_write_batch: Error sending AMC RPMH requests (-110)
qcom_icc_bcm_voter_commit -> qcom_icc_set -> icc_set_bw
camss_runtime_resume -> csiphy_set_power_legacy -> video_prepare_streaming
```

cam 的 SWIspWorker 阻塞在 `icc_set_bw`，随后观察到 UFS clk-gating、jbd2、
调频和 PM 工作线程处于 D 状态。网络与 shell 内建命令仍响应，读取外部程序及
普通重启命令不能完成。已保存失败日志并请求物理重启恢复；这不是成功重启记录。
当前证据不能区分全尺寸特有问题、重复启停 runtime PM 问题或共享互连/电源问题。

用户随后恢复到安卓，已通过无线 ADB 确认 fuxi 正常启动，再以 `adb reboot recovery`
进入 Linux。根文件系统为读写状态，日志记录上次非正常关机后的 journal 替换；
没有执行离线 fsck，不能据此声称完整文件系统检查通过。已恢复 std2 为运行和默认
内核、chg3 为回退，保留相机实验包。第二次正常重启后未见新的 EXT4 I/O 或 RPMh
超时记录，`fuxi-health.sh --require-wifi --require-sensors` 失败项为 0，
日志为 `work/claude-logs/health-20261108-012823.log`。启动确认
`pending=0 tries=0 once=0`，udev 规则校验 1/1 通过，采样未见 D 状态进程。
这是 cam4 测试前的恢复验收，不能代表下述新故障后的状态。

## cam4 对照与再次阻塞

cam4 只增加 RPMh 超时批次诊断并启用可选 trace 支持，没有修复互连逻辑。
普通 fuxi 用户、libcamera v0.7.0、默认未标定 tuning；下表除注明外不保存帧文件。

| 对照 | 观察结果 |
|---|---|
| RAW 2104×1560 | 连续 600 帧完成，约 60 fps；另有 5 次独立启动各 5 帧完成 |
| RAW 4208×3120 | 10 帧完成，约 30 fps |
| 默认 GPU RGB 2104×1560 | 有 120 帧通过记录，但多次在 14、15、24、56、126 帧附近停住；timeout 后通常可正常退出并 runtime suspend |
| GPU RGB 4200×3120 | 一次 30 帧通过；不代表反复启停可靠 |
| GPU RGB + CPU latency 300 us | 600 帧目标在第 56 帧停住，35 秒 timeout，退出 124 |
| GPU RGB + 去除 Agc 的临时 tuning | 600 帧目标完成 54 帧后停住，40 秒 timeout，退出 124 |
| CPU RGB 2104×1560 | 300、1200 帧分别完成，约 30 fps；后续重新启流的 300 帧也完成 |
| CPU RGB 全尺寸 | 请求 4208×3120 调整为 4200×3120；120 帧目标未返回应用首帧，复现下述互连故障并触发用户态断言 |

CPU 模式使用 libcamera 官方环境变量 `LIBCAMERA_SOFTISP_MODE=cpu`，未修改系统
全局配置。CPU/GPU 输出均为 ABGR8888，但 2104×1560 的 bytesused 分别为
13,128,960/13,178,880，对应行步幅 8416/8448 字节。结果提示应继续比较软件 ISP、
缓冲区布局及处理时序，不能据此断言 GPU 驱动是唯一根因，也不能将 CPU 模式当作修复。

CPU latency 线索来自 [CAMSS QoS 上游补丁](https://lists.openwall.net/linux-kernel/2026/11/07/178)，
本轮只临时打开 `/dev/cpu_dma_latency` 并写入 300，退出时关闭；没有应用内核补丁。
去 Agc 的配置也仅放在 `/tmp/fuxi-cam4-no-agc`，测试后已删除。

全尺寸 CPU 测试在 uptime=1188.320 秒进入 CAMSS runtime resume，约 10 秒后报告
`RPMh batch 0 timed out (6 commands)`。对照设备 command DB 得到：

| 地址 | 资源 | data | wait |
|---|---|---|---|
| 0x50000 | MC0 | 0x60b87bf1 | 1 |
| 0x50008 | SH1 | 0x20000001 | 0 |
| 0x50004 | SH0 | 0x60b87c82 | 1 |
| 0x50034 | MM1 | 0x20000001 | 0 |
| 0x50030 | MM0 | 0x6139c9cf | 1 |
| 0x50068 | ACV | 0x60000008 | 1 |

这是整个超时批次的命令列表，不能据此确定哪条命令或哪项硬件最先出错。
调用栈仍为 `camss_runtime_resume -> icc_set_bw -> qcom_icc_bcm_voter_commit ->
rpmh_write_batch`。随后 UFS、jbd2、调频和 PM 线程处于 D 状态。cam 还出现
`std::array<double, 1024>::operator[]` 越界断言；没有有效用户态回溯，不能确定具体
算法或与互连故障的因果关系。该次目标没有完成，timeout 也未能恢复系统。

原始证据保存在忽略目录 `work/camera-20261108/`：
`cam4-rpmh-failure-dmesg.log`、`cam4-rpmh-failure-trace.log`、
`cam4-rgb-cpu1200.log`、`cam4-rgb-cpu-restart.log` 及各 GPU 对照日志。
独立 ftrace instance 的 tracing/events 已关闭，最终 ring 快照各 CPU overrun 和
dropped 均为 0；早先 trace_pipe reader 曾 `Bad address` 退出及出现拼接异常，
不能把整轮流式日志称为完整无损。gdb 一次 attach 已退出进程失败，另一次抓到的
是仍在采集时的栈，均不能充当停帧现场回溯。

另一次 `.bin` 900 帧尝试约 407 帧时因 `/tmp` 满而停止，5.3 GB 临时文件已删除；
该次不计入稳定性验收。后续长测均不保存文件。

最新恢复状态：故障前已预置 default=std2、fallback=chg3，pending=1、tries=0、
once=0。故障后仍能读取这两个启动条目，但启动计数读取和正常 recovery 重启请求
没有完成；尚未确认重启回 std2，也尚未做故障后的健康验收。需要物理重启恢复。

## 后续顺序

1. 先物理恢复并重新验收 std2；相机内核继续保留独立实验条目，不晋级默认。
2. 按 cam4 六条 BCM 命令定位 CAMSS runtime PM/ICC/RPMh 启停故障；核对其他
   线程栈及其与 GPU、UFS 的共享路径。不要靠删除带宽投票掩盖故障。
3. 再分开验证 RAW 各模式、重复启停、RGB、桌面取景、长时间采集与故障恢复。
4. 补有依据的 sensor helper、曝光延迟和标定；核实 native/crop 几何后再实现
   selection API，不填猜测值消除告警。
5. 完成超广角验收后推进主摄驱动、前摄 ID、长焦 CCI 稳定性及 AF/OIS。
