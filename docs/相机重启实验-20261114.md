# 相机同进程重启与 EGL 清理（2026-11-14）

本轮增加 libcamera `0003` context 生命周期候选。原生 ARM64 构建及上游测试
通过，主机 Mesa llvmpipe 的七组、共 700 次启动尝试通过；**手机端补丁版
同进程重启尚未验收**。手机在原版对照的第二次 STREAMON 时复现 MM0 超时，
此时尚未运行补丁版采集。HF 时钟候选不能视为 MM0 修复。

## 修改与离线验证

配方：[libcamera-gpu-lifecycle](../packaging/experiments/libcamera-gpu-lifecycle/README.md)。
`0001` 为首帧参数初始化，`0002` 为逐帧图像和错误缓冲回收；本轮 `0003`
增加停止及失败时 context 释放，shader/program 失败清理与句柄清零，检查
make-current 返回值、空配置和空 shader/link 错误日志。保持共享 EGL display，
不调用 `eglTerminate()`。未安装系统库，也未修改标准内核配方。

`0003` SHA256：`7ca6dcab9ac0b7d2d61579fc27bde7f1e27a1b93cf7ac11b637adb0a4d9a4de5`。
固定源码归档和三个补丁的重放校验通过。

手机故障前完成原生构建：360 个构建步骤，上游测试 45 通过、1 预期失败、
29 跳过、0 失败。手机客户端分别链接 `0001+0002` 和 `0001+0002+0003` 的
隔离构建。编译和上游测试不能证明相机硬件工作流正确。

主机使用隔离容器、Ubuntu 20261107 软件源快照、GCC 15.3.0、Mesa 26.2.4，
渲染器为 `llvmpipe (LLVM 22.1.8, 256 bits)`。测试直接调用真实 `DebayerEGL`，
不创建 CameraManager，不访问手机或摄像头。每组在同一实例执行 100 次启动尝试，
检查停止后的资源计数、重复停止、失败返回前清理，以及另一个 context 仍可使用。

| 场景 | 启动结果 | 清理结果 |
|---|---|---|
| 正常启停 | 100 次成功 | 全部通过 |
| context 创建失败 | 1 次注入失败，99 次成功 | 全部通过 |
| EGL 配置为空 | 1 次注入失败，99 次成功 | 全部通过 |
| 初始 make-current 失败 | 1 次注入失败，99 次成功 | 全部通过 |
| 顶点 shader 失败 | 1 次注入失败，99 次成功 | 全部通过 |
| 片段 shader 失败 | 1 次注入失败，99 次成功 | 全部通过 |
| program link 失败 | 1 次注入失败，99 次成功 | 全部通过 |

总计 694 次成功启动、6 次预期失败。各检查点 context/shader/program 存活计数
及无效删除计数为 0，故障组均确认注入恰好一次。未测试真实图像绘制、DMA-BUF
导入、手机 Adreno、系统挂起或桌面集成，不能替代它们的验收。
测试源和审计库以 `-Wall -Wextra -Werror` 构建；两个新增 shell 矩阵通过
ShellCheck。主机严格回归 354 项脚本测试和 62 项 SuperTerm 测试通过。

同一个离线测试也链接 `0001+0002` 的未修复对照构建：100 次启动均成功，
停止后审计为 `created=100 destroyed=0 live=100`；重复 stop 累计 100 次
无效 program 删除，程序报告 FAIL、退出 1。该反例验证测试能发现真实的旧行为，
不是只检查候选是否能编译。计数取自对象析构前的停止检查点。

## 手机故障

运行内核 `7.4.0-rc1-fuxi-cam6hfclk`。启动确认后已预设下次默认 deb9、
回退 deb8，才开始采集。第一个测试使用 `0001+0002` 的对照库，目标为同一
Camera 对象重复 3 次、每次 30 帧；不是 `0003` 候选。

- 第一次完成 30 帧、stop 返回 0；审计为 context 创建 1、销毁 0、存活 1，
  shaders/programs/invalid_deletes 均为 0，确认停止时 context 未释放。
- 第二次 STREAMON 在 CAMSS runtime resume 中触发 `icc_set_bw()`，
  经 BCM voter 进入 `rpmh_write_batch()`，在启动后约 131.540 秒报告超时。
- TCS 0 的 MM0 地址 `0x50030`、data `0x6139c9cf`，要求响应、已发出、
  未完成。同批次 MC0、SH0、ACV 要求响应且已完成；SH1/MM1 不要求响应。
- TCS enable `0x3f -> 0x3f`，IRQ `0 -> 0`。MM0 地址/投票与历史故障相同，
  但 MC0/SH0 data 不完全相同，不能宣称整个批次或全部消费者状态已对齐。
- 随后可见 GPU worker、PM、调频、UFS clock-gating、jbd2 等线程持续 D 状态，
  等待点包括 `icc_set_bw`、`rpmh_rsc_send_data`、`bio_queue_enter`。
  180 秒测试 timeout 及 SIGKILL 没有使卡在内核的线程完成退出。

此次故障排除了“加入 HF PM 时钟后就已经解决 MM0”的结论。原先成功窗口
MM0 为 `0x6233c9cf`，本次失败为 `0x6139c9cf`；仍需核对显示/其他消费者、
HF 路径时钟和电源域状态，不能删除投票、跳过响应或保持永久 PM 引用来宣称修复。

## 恢复与下一步

已将完整 dmesg 保存到主机忽略目录 `work/camera-restart-20261114/rpmh-dmesg.log`。
clk/ICC 现场读取未返回，目标日志为 0 字节，不作为时钟状态证据。
已结束主机侧两个挂起的 SSH 会话，但不声称远端 D 状态任务已退出。

普通 `systemctl reboot --reboot-argument=recovery` 在主机 12 秒限时内没有返回，
后续 SSH 查询亦超时。**本轮结束时未确认恢复 deb9，最后确认仍为 cam6hfclk
故障现场，需要手机端恢复后复核。** 未使用强制 SysRq、重启桌面、清除 BCB、
改槽位或写 Android/固件分区。

恢复后先确认运行/默认 deb9、回退 deb8，检查启动确认、失败服务、文件系统和
D 状态，再继续内核诊断。不要直接重跑已知会阻塞互连的 restart-matrix。
同进程启停的手机验收、四摄、AF/OIS、画质和拍照录像工作流仍未完成。
