- PAL `allocateVoiceFrontEndIds` 分配了前端 107 和 109（RX 和 TX 各一个会话；AGM 日志里 `sess_id 107, aif id 31` 和 `sess_id 109, aif id 5`）。

## 对主线实现的含义【推测】
- 主线要做的事不只是"设 VSID"：要在 q6apm 建完整的语音 RX/TX 子图（模块 7001000、700100e、7001019、7001005、7001003、7001032 等）、选后端 CODEC DMA、加载 ACDB。这与此前缺口调研的第 1–3 项一致。
- AP 侧的启停时机应跟 Android 一致：**拨出时**就启动语音图，不是接通后。守护进程要监听 VOICE 的 `origination` 状态。

## 追加分析：GPR 包解码（只读，主机上，脚本 `scripts/fuxi-gpr-decode.py`）
strace 的 fd 8 是 audio_pkt 的 GPR 通道（write = AP→ADSP，read = 回包），共 2118 个包。头部格式与内核一致，opcode 对得上 `audioreach.h`：GRAPH_OPEN 0x01001000、PREPARE 0x01001001、START 0x01001002、STOP 0x01001003、CLOSE 0x01001004、SET_CFG 0x01001006、SHARED_MEM_MAP_REGIONS 0x0100100c。【已证实】

- 一次语音拨出建了 3 个新图（GRAPH_OPEN 来自 GPR 客户端端口 0x2011、0x2012、0x2013）。AGM 日志给出各图的硬件端点模块：miid 466f（mid 700100f）、miid 4120（mid 700100e）、miid 43af（mid 7001024）。其中 0x2012 和 0x2013 的 GRAPH_OPEN 的包体只有 16 字节，图定义放在共享内存（先有 0x0100100c 映射），strace 看不到图的内容。
- **VCPM（目标模块实例 0x4，即 `VCPM_MODULE_INSTANCE_ID`）收到了 SET_CFG**，这是缺口调研里"难点是 VCPM 参数格式"的答案，【已证实】到字节：
  - param `0x080011bc`，4 字节：`0x11dc5000`，**即 VSID，卡 2 用的是 0x11DC5000**（先前从 `resourcemanager_kalama_mtp.xml` 推出的副卡值，这次直接在线上看到）。
  - param `0x08001310`，8 字节：`{vsid, 2}`；通话中再发一次 `{vsid, 1}`。第二个字段是什么状态含义【推测】，只能看出它在语音图启动前后由 2 变 1。
  - param `0x0800116b`，32 字节：`{vsid, 3, {0x08000166, 3}, {0x080011b6, 0}, {0x08000167, 0}}`，第二次发时第一对的值由 3 改成 1。每对是（param id，值），含义【推测】是各通道/路径的使能状态。
  - 这三种 param 在整通电话里共出现 8 次（拨出建图时 4 次，切换音频路由时 3 次，另有 1 次）。
- 由此，主线 q6apm 要做的 VCPM 部分很小：向 module 0x4 发这三种 SET_CFG，VSID 用 0x11DC5000（卡 1 是 0x11C05000）。图本身（3 个子图的容器和模块连线）仍要从 ACDB/AGM 的图定义里取，因为它在共享内存里。【推测】
- 另外：strace 只能读 AP→ADSP 的普通包。大块配置（SET_CFG 的 16 字节包体、GRAPH_OPEN）是共享内存传递，需要在 Android 里读 `/vendor/etc` 下 AGM/ACDB 的图定义文件（只读文件）才能还原。
